# 装饰层布局炸裂根治说明（chat-app-deco）

> 用户原话精炼：
> 「截图上消息页整个挤掉了，右边一张大图。之前修了一次，发现是图片是 1600px 的，
> 改成两位数 px 的了，没想到还会发生这种问题。」

## 一、症状

聊天 App「消息」页布局整体炸裂：

- 左侧手写字装饰（Live a good life…）失去定位，竖排挤在屏幕左缘；
- 消息页标题 / 筛选标签 / 问候区被压成一条窄竖列；
- 右侧一张巨大的装饰图占据大半屏幕；
- 同期常伴「聊天图标点了没反应、进不去」（见第四节）。

## 二、根因：装饰层在全部 CSS 里零定义，「改小图片尺寸」只是治标

聊天 App 的 DOM 层级（`index.html`）：

```html
<div id="miya-chat-app" class="miya-chat-app ...">   <!-- display:flex; flex-direction:column -->
  <div class="soft-deco">…系统装饰（手写字/花纹）…</div>
  <div class="chat-app-deco" data-chat-app-deco>      <!-- ← 用户装饰层 -->
    <div class="chat-app-deco--builtin-doodle-msg"></div>
    <div class="chat-app-deco--builtin-doodle-mine"></div>
  </div>
  <div class="qq-pages">…消息/动态/联系人/我的…</div>  <!-- flex:1 -->
</div>
```

用户装饰层由 `js1/miya-chat-app-beautify.js` 的 `renderDecoLayer()` 填充，
每张装饰图写成：

```js
'<div class="chat-app-deco__item" style="left:…px;top:…px;width:…px;height:…px;z-index:…;opacity:…">'
```

**`left/top` 这类内联样式只在 `position: absolute` 下才有意义** —— 设计意图显然是
一个悬浮覆盖层。但全项目检索（css/、index.html 内嵌样式、JS 注入）确认：

> `.chat-app-deco`、`.chat-app-deco--builtin-doodle-*`、`.chat-app-deco__item`
> **在所有 CSS 里一条规则都没有**（`miya-chat-app-beautify.css` 里只有美化面板
> 自己的 `.cab-deco-*` 表单样式）。

于是装饰层退化为 flex column 里的**普通文档流块**：

1. 用户在「美化 → 装饰」上传一张图，尺寸设为 1600×1000；
2. `.chat-app-deco__item` 按 `width:1600px;height:1000px` **实占布局空间**；
3. `.qq-pages`（`flex:1; min-height:0`）被挤到只剩 0–154px 高 —— 消息页内容
   全部压扁；装饰图自身溢出屏幕，表现为右侧一张巨图；
4. 部分装饰 CSS / 主题 CSS 在异常状态下未生效时，`.soft-deco__quote`
   （INS 主题下本应 `display:none !important` 的手写字）也一并显形，
   就是截图里左上角的竖排英文。

**为什么上次「改成两位数 px」会好、后来又复发**：把装饰图尺寸改小只是把文档流
占位变小，装饰层「参与布局」这个错误本身没有修 —— 换一张图、调大尺寸、
恢复备份，或者某条 `w:80` 的默认装饰项累加，症状就会回来。
**这是治标，且注定复发。**

## 三、修复：让装饰层回到「悬浮、不参与布局」的设计语义

`css/miya-chat-app-beautify.css` 末尾补齐装饰层定位约束：

| 选择器 | 规则 | 作用 |
|---|---|---|
| `#miya-chat-app .chat-app-deco` | `position:absolute; inset:0; overflow:hidden; pointer-events:none; z-index:2` | 容器永远覆盖全屏、裁剪溢出、不拦截点击 |
| `#miya-chat-app .chat-app-deco--builtin-doodle-msg / -mine` | 同上 | 内置涂鸦层同样零布局占位 |
| `#miya-chat-app .chat-app-deco__item` | `position:absolute` | JS 内联的 left/top/width/height 从此有定位语义 |
| `#miya-chat-app .chat-app-deco__item img` | `width/height:100%; object-fit:fill; display:block` | 与「上传后设页面、位置与尺寸(px)」的拉伸语义一致 |

层级：`.soft-deco`（系统装饰）= 0、`.qq-pages`（内容）= 1、用户装饰 = 2
（装饰图列表的 z 0–999 在容器内部继续分层）。`pointer-events:none` 与
`injectGuardCss()` 里既有的 `!important` 兜底双保险。

修复后的效果：**无论装饰图设多大（哪怕 1600px），最坏情况是被容器裁剪，
绝不再挤动消息页一像素。**「改小尺寸」从「维持不崩的手段」变回「纯粹的审美选择」。

## 四、关于「更新完进太急：图标点了没反应 / 布局乱」

这是叠加在上述缺陷上的第二个因素，机制在第五批（SW 派发治理）已完整分析过：

1. **更新交替期**：页面刚打开时浏览器检测到 `sw.js` 变化 → 新 SW 后台
   install + `skipWaiting` 接管 → 期间已加载的旧 JS 与新拉取的 HTML/CSS
   可能短暂混杂；模块初始化失败时，图标点击就会无声无息。
2. **网络抖动回退**：CSS/JS 是 networkFirst，请求失败时回退缓存副本。
   新 HTML + 旧 CSS 的组合下，`.soft-deco__quote` 这类「新版才隐藏」的
   元素就会显形 —— 截图里的手写字正是旧 CSS 的指纹。
3. 本项目已有版本哨兵（SW build 广播 → 页面自动刷新一次）兜底大部分窗口期，
   但**更新完成的瞬间立刻打开**仍是最容易撞上混杂状态的时机。

**给用户的操作建议**：更新包之后第一次打开链接，如果界面有异样（布局乱、
点不动），**下拉刷新或杀掉页面重进一次**即可 —— 那是哨兵在换血，不是项目坏了。
本次修复已 bump 全套版本号（见下），换上后旧缓存会被一次性清干净。

## 五、A/B 对照（真实 Chromium，390×844 手机视口）

注入同一张 1600×1000 装饰图（`page:'all'`, `z:5`, `opacity:1`）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `.chat-app-deco` computed position | `static`（文档流） | `absolute`（悬浮） |
| 装饰层实占高度 | **1000px**（布局空间） | 844px（= 视口，裁剪层） |
| `.qq-pages` 高度 | **0px**（消息页被挤没） | **844px**（占满全屏） |
| 视觉 | 消息页压成顶部一条 + 巨图占屏 | 顶栏/筛选/底栏全部正常，装饰图悬浮 |

结论：修复前布局炸裂复现 ✓，修复后正常 ✓（`broken_before=True, broken_after=False`）。

## 七、教训

> **「改一个数值能让症状消失」不等于「数值就是病因」。**
> 1600px 只是压垮布局的那根稻草，真正缺的是撑住装饰层的定位规则 ——
> 上次的修复删掉了稻草，桥还是空的。修完应该追问：装饰层为什么能参与布局？
> 它的设计语义（悬浮覆盖）在 CSS 里兑现了吗？一条 `grep` 就能回答，
> 但要先把「症状没了」和「病好了」区分开。
