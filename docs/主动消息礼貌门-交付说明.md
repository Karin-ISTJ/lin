# Karin · 主动消息礼貌门

本次改动给「角色主动找你」这件事补上两道分寸感，并修掉一个属性转义的注入隐患。
全部改动都带可重跑的回归测试，且通过 A/B 对照验证（把实现改坏，测试必须变红）。

---

## 一、这版做了什么

### 1. 打字时不打扰（新增）

**问题**：主动消息的时机由程序决定，但「用户此刻在做什么」只有界面知道。
你正在输入框里写一段长回复，角色突然插一条主动消息进来 —— 轻则打断思路，
重则那次重渲染会重建输入框，草稿受影响。

**现在**：焦点在可输入元素里、且里面有实际内容时，这一轮主动消息自动跳过。
等你写完（输入框清空 / 失焦）下一轮自然恢复。

判定刻意做得**宽**（宁可少发一次，也别在人家打字时插嘴）：

| 场景 | 是否压制 |
|---|---|
| 焦点在输入框里且有字 | ✅ 压制 |
| 焦点在输入框里但是空的 | ❌ 不压制（人只是点了一下） |
| 输入框里只有空格/换行 | ❌ 不压制 |
| `contenteditable` 区域有内容 | ✅ 压制 |
| 按钮 / 普通 div | ❌ 不压制 |

不看具体 id（输入框有 `xw-writer-input`、`qq-room-input` 多个），按「标签 + contenteditable」判，
以后加新输入框不用回来改这里。查询失败一律当作「没在写」——
不能因为判定出错就永久不发消息。

> 代码：`js1/miya-chat-background.js` 的 `isUserComposing()`

### 2. 每日主动上限（新增）

**问题**：原本只有「两次之间至少隔 N 分钟」+「静默时段」两道约束。两条都满足时，
理论上可以一整天不间断地发 —— 页面挂着不管，回来就是满屏「在吗」。

**现在**：多了一个每日上限，**默认 0 = 不限**（所以升级后行为与升级前一模一样）。

- 位置：聊天设置 →「记忆与后台」→「后台消息」→「每日上限」
- 位置：设置 →「默认值」→「后台消息」→「每日上限」（全局默认）
- 按**本地日期**跨天自动归零
- 与间隔限制**叠加**生效，两个条件都满足才会发
- 静默时段管「几点发」，每日上限管「一天几条」，互不替代
- 计数只在**消息真的发出去之后** +1 —— 生成失败、接口没配、忙线挡掉都不占额度

> 代码：`js1/miya-chat-background.js` 的 `withinDailyCap()` / `localDayKey()`；
> 字段定义在 `js1/miya-chat-store.js` 的 `backgroundMessage`

### 3. 属性转义修漏（修 bug）

**问题**：`esc()` 只转义 `& < > "`，**不含单引号**。而预约模块有一处把头像 URL
拼进**单引号属性**里 —— 值里带 `'` 就能提前闭合属性、注入新属性。

**修复**：新增 `escAttr()`（补齐 `'` → `&#39;`），把该处从 `esc()` 换成 `escAttr()`。

> 代码：`js1/miya-appointment-app.js`

## 二、测试

新增两个测试文件：

| 文件 | 类别 | 断言数 | 验什么 |
|---|---|---|---|
| `test/proactive_courtesy_gates.py` | 静态/Node | 71 | 函数逻辑、源码接入点、UI 开关、名单一致性、A/B 守卫 |
| `test/e2e_proactive_courtesy_gates.py` | 浏览器 | 19 | 两道门在**真实流程**里拦/放 |

### 单测覆盖

- 源码层面：两道门真的挂在 `triggerReply` 上、顺序正确、都是「跳过」不是「失败」
- 数据层：三个新字段的默认值与归一化；`maxPerDay` 默认 0（升级不改行为）
- **名单一致性**：`dayKey` / `dayCount` 必须同时在
  `miya-chat-store.js` 的 `chatLevelBgKeys` 和 `miya-chat-global-settings.js` 的
  `CHAT_LEVEL_BM_KEYS` 里 —— 这是本项目踩过两次的坑（`farm`、`timeEvents`），
  漏登记的表现是「明明发过 3 条，上限还是拦不住」
- UI：两个面板的渲染/读取/回填三处齐全，且有 0..200 夹取
- 计数算法：当天累加、跨天从 1 重算、失败路径不计数

### 集成测试覆盖

从页面里真调一次 `kickScan()`，看**副作用**：

| 场景 | 期望 |
|---|---|
| 基线（不限次数、无人干扰） | 放行 |
| 用户正在打字 | 拦下 |
| 打完字（输入框清空） | 放行 |
| 今天已满额 | 拦下 |
| 上限提高 | 放行 |
| 昨日残留计数 | 放行（跨天作废） |

判据是 `lastProactiveAttemptAt` 变不变 —— 门拦住时是静默跳过，
不写这个字段也不写失败标记，所以「变/不变」就是最干净的探针，
不需要为了测试去暴露内部函数。

### A/B 对照

- 单测：把 `withinDailyCap` 改成恒 `true` → 2 项「拦住」断言变红；
  把 `isUserComposing` 改成恒 `false` → 5 项「压制」断言变红
- 集成：把两道门从 `triggerReply` 里摘掉 → **恰好** 2 项「拦住」断言变红（19 → 17 通过）

## 三、两个设计上的坑（写下来免得后人再踩）

### 配置型字段 vs 会话运行时字段，走两条不同的写入路径

这个项目里 `backgroundMessage` 混着两类字段，混用会「存得进去、读不出来」：

| 类别 | 字段 | 正确写入路径 |
|---|---|---|
| **配置型** | `maxPerDay`、`activeEnabled`、`activeIntervalMin`、`quiet*` | `miyaChatGlobalSettings.savePerContact`（登记为该联系人的覆盖） |
| **会话运行时** | `dayKey`、`dayCount`、`lastProactiveAttemptAt`、`lastPushFailAt` | `store.saveChatSettings`（写进 `chat.chatSettings`） |

原因：

- 配置型字段若直接用 `saveChatSettings` 写，会被 `getChatSettings()` 末尾的
  `applyToChatSettings` 用全局 slice 盖回模板默认值（`maxPerDay` 变 0）。
- 会话运行时字段若走 `savePerContact`，会被 `CHAT_LEVEL_BM_KEYS` 主动剔除，
  写进去也没了。

### 为什么集成测试不断言「dayCount +1」

计数只在**真的把消息发出去**（`recordAutoPushAt` 分支）时才 +1。
测试环境没配 API，发送必然停在 `api_not_configured` 的失败路径上，
计数按设计不该动。所以那条断言放在单测里用桩 store 覆盖，集成测试只验拦/放行为。
