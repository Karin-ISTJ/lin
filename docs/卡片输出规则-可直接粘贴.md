# 卡片输出规则 · 世界书条目（可直接粘贴）

这个文件里有**两段**可粘贴规则，各管一件事，可以只用一段，也可以都粘：

| 复制区 | 作用 | 要粘吗 |
|---|---|---|
| 【复制区 A】状态卡片 | 回复末尾输出 `[类型\|字段…]` 结构，渲染成人物/任务/邮件卡片 | 想要卡片就粘 |
| 【复制区 B】现实时钟事件 | 需要现实等待的事（利息/快递/预约…）按真实时间结算，到点弹到账卡 | 想要「过几天回来收利息」就粘 |

两段互不干扰，**都粘进同一条世界书条目**即可。

---

## 【复制区 A】状态卡片 · 从这里开始复制

```
# 状态卡片输出规则

每次正文回复的末尾，必须输出一个状态卡片模块，用 <card> 和 </card> 包住。
标签内只允许出现本规则定义的纯文本结构，禁止使用任何 Markdown、HTML 或多余的说明文字。

固定格式如下：

<card>
[Profile|姓名|身份头衔|等级或进度|资源或声望|一句话当前心境]

[Intel]
[Pinned|单个Emoji|标签名|标题|详情|行动指引]
[Card|分类|标题|详情|行动指引]

[NPCs]
[NPC|姓名|身份称号|好感度或与我的关系|这个人的内心独白]

[Mails]
[Mail|发信人|日期|信件标题|信件正文|署名|随信物品（没有就留空）|物品说明（没有就留空）]

[Quests]
[MainQuest|主线目标名称|进度|目标说明|奖励]
[SideQuest|支线委托标题|限时或状态|委托说明|报酬]

[Todos]
[Todo|0或1|待办事项]

[Board]
[Post|发帖人|身份称号|标签|告示标题|详细说明]
[Reply|回帖人|时间|回帖内容]

[Choices]
[Choice|建议正文|一句话补充]
</card>

## 剧情建议（Choices 分区）

这一区给用户**四个「接下来可以怎么做」的选项**，他会点其中一条直接发出来。

写法：

```
[Choices]
[Choice|我把伞递过去，问她要不要一起走|顺势拉近关系]
[Choice|假装没看见，先回自己工位|保持距离]
[Choice|反问她刚才那句话什么意思|把话摊开]
[Choice|约她周末去上次说的那家店|推进到私下相处]
```

要求：

1. **必须四条**，不多不少。少于四条时这区会显得残缺，多于四条用户反而选不动。
2. **第一条字段是「用户要说/要做的话」**，用第一人称写，写成能直接发出去的一句/两句
   完整发言 —— 因为它会被原样当作用户消息发送，不是给你看的提示。
3. 第二条字段是**一句话补充**，说明这个选择大概会走向什么，10 字左右，只用于展示。
   可以不写，但建议写，用户靠它判断选哪条。
4. 四条之间**要有真实分歧**：不同的态度、不同的推进速度、甚至不同的风险。
   不要写成「温和版 / 更温和版 / 最温和版」这种同一件事的三种说法。
5. 面向**角色**说话，不要写成「用户会…」这样的第三人称旁白。
6. 每条尽量控制在一句话内。太长的建议用户读完就累了。

> 这一区可以不放。确实现不出四个有分歧的选择时，宁可不写，
> 也不要硬凑四条雷同的。

## 填表要求

1. **分隔符**：每行条目内部一律用半角竖线 `|` 分隔字段，字段数量必须与上面完全一致。
2. **分区标题**：`[Intel]` `[NPCs]` `[Mails]` `[Quests]` `[Todos]` `[Board]` `[Choices]` 这类单独成行的方括号是分区名，**不要**在里面填数据。
3. **待办勾选**：`[Todo|1|xxx]` 表示已完成，`[Todo|0|xxx]` 表示未完成。
4. **留空**：某个字段没有内容时留空即可（例如 `[Mail|老王|三日|问候|近来可好|老王||]`），但竖线要保留。
5. **条数**：只输出当前实际存在的内容。某一类确实没有时，可以整个分区不写。
6. **不要解释**：标签外不要加「以下是状态卡片」之类的话，正文写完后直接接 <card> 块。
7. **闭合标签必须写** `</card>`。漏掉不会报错，但会把后面的内容一起吞掉。
```

## 【复制区 B】现实时钟事件 · 从这里开始复制

```
# 现实时钟事件规则

用户可能隔好几天才回来继续剧情。现实时间是他手机上的真实时间，
不会因为剧情跳天而加快，也不会因为他没来而暂停。
所以需要等待的事，应该按真实时间到期——而不是在剧情里演一遍。

## 什么时候声明事件

当剧情中出现「本身就需要现实时间等待才有结果」的事，在回复末尾追加事件声明。
典型场景：存钱生息、买东西等发货、送修、托人办事、等审批、
约好的时间点、种植、发酵、旅行出发、比赛、考试。

**不要**声明能立刻给的东西：礼物、惊喜、告白、各种浪漫奖励。
能马上给的东西不该让用户等——这条是硬规则，写了也会被系统丢弃。

## 声明格式

必须是合法 JSON，用 <miyaevent> 和 </miyaevent> 包住，单独占一行：

<miyaevent>{"type":"bank_interest","title":"定期存款利息","description":"存入后 7 天可领取利息","result":"到账 +86 铜币","afterDays":7,"needsClaim":true}</miyaevent>

字段说明：

- type：事件类型，从下面选一个
  bank_interest 银行利息 / investment 投资结算 / refund 退款 /
  salary 工资 / settlement 结算 / delivery 快递 /
  subscription 会员订阅 / lease 租期 / plant 种植 /
  fermentation 发酵 / repair 维修制作 / commission 委托 /
  application 申请审核 / appointment 预约 / ticket 演出电影 /
  match 比赛 / travel 旅行 / exam 考试 / general 事务
  （优先用上面 18 个具体类型；general 是兜底桶，要求标题或说明里
   带现实事件关键词，否则会被丢弃。能对上具体类型就别用 general。）
- title：事件名，简短（如「定期存款利息」）
- description：补充说明，可省略
- result：到期时显示成什么结果（如「到账 +86 铜币」「已送达驿站代收点」）
- afterDays / afterHours / afterMinutes：从现在起多久后到期，三选一填数字
- needsClaim：true 表示到期后要用户点「领取 / 确认」才算数；
  省略或 false 表示到期直接算成（快递、通知这类用 false）

## 输出要求

1. **不要在正文里播报事件**。正文该写什么写什么，声明放在正文最后。
   系统会自动把它渲染成正文上方的卡片，不需要角色开口说「我记下了」。
2. **只声明真的需要等待的事**。立刻能给的礼物、惊喜、告白一律不要写。
3. **同一件事不要重复声明**。已经声明过的，后续回复不要再写一遍。
4. 一次回复最多 1~2 条，没有就不写这个标签。
5. **闭合标签必须写** `</miyaevent>`。漏掉会把后面的内容一起吞掉。
6. 标签外不要写别的 JSON，也不要解释这段是什么。
```

## 替换成你自己的题材

上面是通用模板。**要换成你自己的卡，只需要改两处**：

**第一处：分区名。** 比如你是侦探卡，把 `[Intel]` 改成 `[线索]`、`[NPCs]` 改成 `[相关人物]`。
渲染器认的是里面的**类型标签**（`Pinned` / `NPC` / `Card`…），分区名显示成什么它照搬什么。

**第二处：字段含义。** 比如 `[Profile|…]` 原本是 `姓名|头衔|等级|资源|心境`，
侦探卡可以当成 `姓名|代号|权限等级|信用点|心境` —— 字段**位置**保持 5 个就行，含义你自己定。

> ⚠️ 唯一要守住的：类型标签用下面速查表里的**标准名**，字段**顺序和数量**别乱。
> 想加自己的类型（比如 `[Hack|…]`）也可以，渲染器会把内容平铺显示，不会丢。

# 格式速查表

## 一、怎么触发卡片

用 `<card>` 和 `</card>` 把整个卡片块包起来，**只有这一种写法**：

```
<card>
[Profile|…]
[NPCs]
[NPC|…]
</card>
```

标记必须写完整。**漏掉 `</card>` 不会报错，但会把标记之后的正文一起吞掉**
（被当作卡片内容，因为不符合 `[类型|…]` 格式而不显示）——
所以卡片的输出规则里一定要强调闭合标签，或让卡片块出现在回复最末尾。

## 二、分区名（单独成行，不含竖线）

这几行只是「开关」的作用，告诉渲染器接下来是哪个分区：

```
[Intel]   [NPCs]   [Mails]   [Quests]   [Todos]   [Board]
```

**同义写法也能认**（大小写不敏感）：

| 你写 | 等同 |
|---|---|
| `[Intel]` `[Info]` `[Intels]` | 情报 |
| `[NPCs]` `[NPC]` `[Characters]` `[Cast]` | 人物 |
| `[Mails]` `[Mail]` `[Letters]` | 信件 |
| `[Quests]` `[Quest]` `[Tasks]` `[Task]` | 任务 |
| `[Todos]` `[Todo]` `[Checklist]` | 待办 |
| `[Board]` `[Boards]` `[Posts]` `[Notice]` | 公告 |

**自定义分区名**：写一个不在表里的名字（如 `[其他线索]`），渲染器会**直接用这个名字**做标题。

> 其实分区标题行**可以省略** —— 渲染器靠类型标签自己归类。
> 但建议保留，这样模型填表时更不容易串行。

## 三、类型标签速查

### 1. 名片（全卡只会用一条）

| 标签 | 字段顺序 |
|---|---|
| `Profile` | `姓名` \| `头衔` \| `等级` \| `资源/声望` \| `心境一句话` |

> ⚠️ 注意：`Profile` 特殊，它**不属于任何分区**，会渲染在最上方。
> 字段含义随你定，但**保持 5 个**。

### 2. 该卡特有的字段顺序总表

| 标签 | 归属分区 | 字段顺序（用 `|` 分隔） |
|---|---|---|
| `Pinned` | 情报 | `Emoji` \| `标签` \| `标题` \| `详情` \| `行动指引` |
| `Card` | 情报 | `分类` \| `标题` \| `详情` \| `行动指引` |
| `NPC` | 人物 | `姓名` \| `身份称号` \| `关系/好感` \| `内心独白` |
| `Mail` | 信件 | `发信人` \| `日期` \| `标题` \| `正文` \| `署名` \| `物品名` \| `物品说明` |
| `MainQuest` | 任务 | `标题` \| `进度` \| `说明` \| `奖励` |
| `SideQuest` | 任务 | `标题` \| `状态` \| `说明` \| `奖励` |
| `Todo` | 待办 | `0或1` \| `事项` |
| `Post` | 公告 | `发帖人` \| `身份称号` \| `标签` \| `标题` \| `说明` |
| `Reply` | 公告 | `回帖人` \| `时间` \| `内容` |

> 大小写不敏感，`[NPC|…]` 和 `[npc|…]` 一样。

## 四、两个容易踩的坑

**坑 1：`Todo` 的第 1 个字段是勾选状态，不是文字。**

```
✅ 正确   [Todo|1|去买菜]      ← 已完成，会显示空心点 + 划掉
✅ 正确   [Todo|0|去买菜]      ← 未完成
❌ 错误   [Todo|去买菜]         ← 会把「去买菜」当成勾选状态，事项变空白
```

除了 `0/1`，也认 `true/false`、`是/否`、`√/×`、`已完成`。

**坑 2：字段数量写少了，后面会串位。**

```
模板   [Mail|发信人|日期|标题|正文|署名|物品名|物品说明]
✅ 好   [Mail|老王|三日|问候|近来可好|老王|自制酱菜|腌了三个月]
✅ 好   [Mail|老王|三日|问候|近来可好|老王||]        ← 没礼物就留空，竖线保留
⚠️ 差   [Mail|老王|三日|问候|近来可好|老王]           ← 少两根竖线，虽不报错但后面字段会缺
```

> 好消息：**写少了不会崩，也不会串到别的地方** —— 缺的字段就是空的。
> 所以「礼物留空」这种情况，写成 `[Mail|老王|三日|问候|近来可好|老王||]` 最稳。

## 五、忘了写分区会怎样

比方说你只写了这一行，前面没有 `[NPCs]`：

```
[NPC|伊恩|接待员|好感 72|这人做菜时倒是难得认真]
```

渲染器会**自动把它归到「人物」分区**（因为 `NPC` 这个类型名认得出）。
所以忘写分区标题顶多是顺序不好看，**内容不会丢**。

## 六、用了渲染器不认识的类型

比如你写 `[Hack|目标防火墙|冷却 3 秒|需先断电]`：

- **不会报错，不会丢内容**
- 会平铺显示在一个分区里，标题用你声明过的自定义分区名（没声明就叫「更多」）

所以想加自己的类型，**放心加**。想要更好看的样式，再用上面表里的标准标签。

# 现实时钟事件 · 速查表

## 一、它和卡片是两套东西，别搞混

| | 状态卡片 | 现实时钟事件 |
|---|---|---|
| 标签 | `<card>…</card>` | `<miyaevent>…</miyaevent>` |
| 内容 | `[类型\|字段…]` 纯文本行 | **JSON** |
| 显示位置 | 回复的那个楼层里 | 场景**正文上方**（不属于任何楼层） |
| 时间 | 剧情时间 | **手机上的真实时间** |
| 会不会自己变 | 不会 | 会（到点自动从未到期变已到期） |

两个标签可以在同一条回复里同时出现，互不影响。

## 二、只有这 19 种类型

```
bank_interest 银行利息    investment  投资结算    refund      退款
salary        工资        settlement  结算        delivery    快递
subscription  会员/订阅   lease       租期        plant       种植
fermentation  发酵        repair      维修/制作   commission  委托
application   申请/审核   appointment 预约        ticket      演出/电影
match         比赛        travel      旅行        exam        考试
general       事务
```

写别的名字不会崩，会被当成 `general`（事务）处理。

> ⚠️ **`general` 有额外门槛，尽量别用。**
> 上面 18 个标准类型，只要类型名选对就直接通过；
> 但 `general` 是「兜底桶」，系统要求它的**标题 / 说明 / 结果**里
> 至少出现一个现实事件关键词（银行、利息、快递、审核、预约、旅行、
> 维修、种植、考试、工资、结算、演出、比赛、发酵…），
> 否则会被当成「编出来的奖励」丢掉。
>
> 所以能对上标准类型就用标准类型，实在对不上再考虑 `general`，
> 并且标题里带上关键词。

## 三、三个时间字段，用哪个

| 字段 | 意思 | 例子 |
|---|---|---|
| `afterMinutes` | 几分钟后 | `"afterMinutes":30` |
| `afterHours` | 几小时后 | `"afterHours":6` |
| `afterDays` | 几天后 | `"afterDays":7` |

**三选一**，填数字。也可以直接给绝对时间 `"dueAt":"2026-09-22 15:00"`，但用相对时间更省事——你不用算今天是几号。

> 一个都不填的话事件不会创建（系统不知道该什么时候到期）。

## 四、`needsClaim` 决定按钮长什么样

| 写法 | 到期后 | 按钮 | 适合 |
|---|---|---|---|
| `"needsClaim":true` | 显示「待确认」 | **领取 / 确认** | 钱、要你点头才算数的事 |
| `"needsClaim":false` 或不写 | 显示「已到期」 | 知道了 | 快递、通知、自己会完成的 |

## 五、到期太久会作废

不同类型有不同的宽限期，过了就变「**已错过**」：

| 类型 | 宽限 |
|---|---|
| 利息 / 投资 / 工资 / 快递 / 维修 等 | 不过期，一直等着你 |
| 预约 | 3 小时 |
| 演出 / 比赛 / 考试 | 6 小时 |
| 旅行 | 12 小时 |
| 事务 | 48 小时 |

道理很直白：**钱可以等你，牙医不会。** 演出开场了你再回来，那场戏就是真的错过了。

## 六、四个容易踩的坑

**坑 1：写成了叙事句，不是 JSON。**

```
❌ 错误   <miyaevent>我在银行存了钱，七天后取利息</miyaevent>
✅ 正确   <miyaevent>{"type":"bank_interest","title":"定期存款利息","afterDays":7,"result":"到账 +86 铜币","needsClaim":true}</miyaevent>
```

**坑 2：在正文里把事件又说了一遍。**

正文该写角色做了什么；事件声明是给系统看的，会自动变成卡片。
两处都写，用户会看到「说了一遍又弹一张卡」。

**坑 3：声明了能立刻给的东西。**

```
❌ <miyaevent>{"type":"gift","title":"一份惊喜礼物",...}</miyaevent>
```

`gift` / `surprise` / `reward` / `romance` / `confession` 这些类型名**直接拒收**；
标题或说明里出现「礼物 / 惊喜 / 送给你 / 告白」也会被拦。
被拦掉不会报错，只是卡片不出现——所以别在这上面浪费 token。

**坑 4：漏掉 `</miyaevent>`。**

跟 `<card>` 一样，漏闭合会把标记之后的正文一起吞掉。**标签一定要写完整。**

## 七、想验证有没有生效

跟卡片一样，最直接的办法是看**场景正文上方**有没有出现卡片。
出现了 = 全对（标签识别、JSON 解析、时间计算、状态机、渲染全走通了）；
没出现 = 要么没声明、要么被拦了（礼物类）、要么 JSON 写坏了。

> 想快速试一次，可以让角色「去银行存一笔定期」，声明 `afterDays:7`，
> 然后临时改成 `afterDays:0` 再发一镜，到期卡立刻就会弹出来。
