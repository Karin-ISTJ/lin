# 已知限制与绕过方法

> 这份文档写给**使用者**，不是开发记录。
>
> 目的：当你遇到某个「看起来像 bug、其实是设计取舍」的情况时，
> 能在这里直接查到 **① 是不是已知的 ② 为什么会这样 ③ 怎么绕开**。
>
> 每一条都标注了它在代码里的出处，方便日后核对是否仍然成立。
> 修好的条目会被划掉并注明版本，不会悄悄消失。

**怎么用**：按 `Ctrl/Cmd + F` 搜你看到的**报错文字或现象关键词**。

## 一、更新与缓存

### 1.1 更新后需要刷新吗？

**基本不需要，但偶尔要刷一次。**

Service Worker 会在检测到自己比页面新时**自动刷新一次**页面
（`sw.js` 的 `skipWaiting()` + `js1/app.js` 的 `location.reload()`）。
同一次会话里最多自动刷一次，避免刷新风暴。

**什么情况下仍要手动刷：**

| 情况 | 该怎么做 |
|---|---|
| 刚替换完文件、页面还停在旧版 | 手动刷新一次（`Ctrl/Cmd + Shift + R` 更稳） |
| 提示里出现「请刷新后重试」 | 照做即可，这是设计好的兜底路径 |
| 同一次会话已经自动刷过一次，还是旧的 | 手动刷 —— 自动刷新有「一次会话只刷一次」的保护 |

> **为什么要有「只刷一次」的保护**：如果不限制，每次 SW 广播都可能触发
> 刷新，页面会陷入刷新循环。代价就是极端情况下需要你手动补一次。
> 出处：`js1/app.js` 的 `miyaHandleSwBuild`（`sessionStorage` 防循环）。

### 1.2 ⚠️ 同一个文件不要重复导入 / 不要重名

**这是本项目最容易踩的一条。**

导入聊天记录、导出后再导入、或者给文件起同名时，会出现
「明明删掉了却提示已存在」这类怪现象。

**怎么做：**
- 一份文件只导入一次；
- 不要给两个不同的卷宗起同一个名字；
- 如果已经撞了，**先刷新页面再操作**（刷新会清掉内存里的旧索引）。

> 出处：`miya-appointment-store.js` 的 `importSession` / 会话名唯一性。
> 这一类问题的共同形态是「内存索引与存储不一致」，刷新即可对齐。

## 二、存储容量

### 2.1 数据到底能存多少？

本项目**分两层**存储，理解这一点能解释大部分「东西不见了」的疑惑：

| 层 | 容量 | 存什么 |
|---|---|---|
| **localStorage** | 约 **5 MB**（浏览器限制，各浏览器略有差异） | 设置、索引、元数据 |
| **IndexedDB** | 通常 **几百 MB ~ 几 GB**（受设备剩余空间限制） | 聊天记录、图片、相册 |

**超过 48 KB（49152 字节）的单个值会自动溢出到 IndexedDB**，
localStorage 里只留一个 `{"__storedInIdb":true}` 的占位标记。
（出处：`js2/miya-storage.js` 的 `SPILL_BYTES`）

> **这不是 bug，是设计。** 如果大值直接塞 localStorage，5 MB 很快用满、
> 之后所有设置都写不进去。

### 2.2 配额写满会怎样？

**不会静默丢数据**，会：

1. 在控制台打一条告警（带是哪个 key 撑爆了、多少字节）；
2. **提示你一次**（30 秒内只提示一次，不刷屏）；
3. 把失败信息记录下来，供诊断面板查看。

**你该怎么做**：删掉一些不用的图片 / 相册 / 旧卷宗，或清理浏览器数据。
**排查入口**：控制台执行 `miyaDiag.show()`，会看到存储失败记录的 key 和连续失败次数。

> 出处：`js2/miya-storage.js` 的 `miyaNotifyStorageFull` /
> `global.__miyaLastStorageError`。

### 2.3 图片会被压缩

**相册**里的图入库时会被压缩：**长边 2560、JPEG 质量 0.92**。
**下载下来的是当年压缩后的版本，原图不会保留。**

> 为什么：不压缩的话，几张手机原图就能把 IndexedDB 撑到几百 MB。
> 2560 / 0.92 是「肉眼几乎无损」与「体积可控」之间的取舍。
> 出处：`js1/miya-chat-album.js` 的 `ALBUM_IMAGE_MAX_EDGE` / `ALBUM_IMAGE_QUALITY`。

**聊天发图**的压缩更激进（长边 1920、质量 0.82）—— 场景是「快速发出、不占带宽」。
> 出处：`js1/miya-chat-image.js` 的 `compressImageFileToBlob` 缺省参数。

**如果你需要原图**：发之前先自己备份一份，系统内不留原图。

### 2.4 隐私模式下存储会失灵

浏览器**无痕 / 隐私模式**下，部分浏览器会直接禁用 IndexedDB 或 localStorage。

**表现**：数据像是保存了，一关页面就没了。
**怎么做**：不要用隐私模式使用本项目。这不是可以修的 bug，是浏览器的限制。

## 三、上下文与记忆

### 3.1 角色「记不住」很早之前的对话

这是**预期行为**，不是 bug。记忆分两级：

| 范围 | 内容 |
|---|---|
| **最近 80 条**（约 40 轮） | 原文，细节完整 |
| **更早** | 只剩「分镜总结」的压缩提要，细节必然丢失 |
| **上限** | 500 条封顶，防止超长会话把上下文撑爆 |

> 出处：`js1/miya-chat-store.js` 的 `memoryCount` / 默认配置注释。
>
> **怎么改善**：把「分镜总结」的触发阈值调小（默认每 10 条触发一次），
> 让远期的沉淀更密。或者手动把重要设定写进角色卡 / 世界书 ——
> 那部分**每轮都完整注入**，不受 80 条窗口影响。

### 3.2 楼层很多时列表会变卡

单次渲染的楼层数默认上限 **100**（`messageRenderLimit`）。
超出部分不渲染，是为了保证滚动流畅。

**表现**：往前翻到很远处，发现更早的楼层像是「没了」。
**它没丢**，只是没渲染。缩小范围 / 用卷宗切换即可。

> 出处：`js1/miya-chat-store.js` 的 `messageRenderLimit`。

---

### 3.3 线下候选的记忆，什么时候才写进记忆表

线下一层角色回复可以点右下角 `‹ ›` **翻出好几个候选版本**。
这几个候选**共用同一个楼层**（它们其实是同一层的内容，不是新楼层）。

这样一来，「这一层该写什么记忆」就有了歧义 ——
你翻到第 2 版、但第 1 版也想留着，记忆表该记哪一个？

**现在的规则：你不选定，就不写。**

| 你要做的事 | 记忆表什么时候更新 |
|---|---|
| 生成了一版，没有再翻候选 | 生成完立即写 |
| 点 `›` 翻出了候选 | **先不写**，等你选定 |
| 翻看候选（`‹` `›` 来回看） | **不写**（翻看不等于选定） |
| **在某一版下面继续发消息** | 这时才把**那一版**的记忆写进去 |
| 在历史楼层（下面已有别的内容）重生成 | 立即写（它早被钉住了，不参与候选延迟） |

一句话：**「继续往下写」才是「我认了这一版」的信号**，翻看不做数。

几个你可能会遇到的现象，都不是故障：

- **点 `›` 之后记忆表一直没动静** —— 正常。等你发下一句消息它才会补上。
- **原版那一条记忆消失了** —— 正常。原版变成候选后，它先前写的记忆会被回收
  （否则「两条时间线」的记忆会同时留在表里）。你选定哪一版，就写哪一版。
- **翻回第 1 版再发消息，写进去的是第 1 版的记忆** —— 正常。
  各候选各自的待写内容是按 `swipes` 的序号**分别保存**的，
  切到哪一版就写哪一版，不会串。

> 出处：`js1/miya-appointment-engine.js` 的 `shouldDeferMemoryForPendingSwipe()`、
> `js1/miya-appointment-app.js` 的 `confirmPendingFloorBeforeSend()`、
> `js2/miya-memory-table-app.js` 的 `commitConfirmedFloor()`；
> 各候选的待写内容记在消息的 `swipeMtRaw`（与 `swipes` 按下标对齐），
> 当前显示那一版的记在 `mtRaw`。

## 四、主动消息的频率

### 4.1 角色可能一整天不停地找你

**已提供开关，默认不限次数。**

主动消息原本只有「两次之间至少隔 N 分钟」和「静默时段」两道约束。
两条都满足时，理论上可以一整天不间断地主动发 —— 你把页面挂着不管，
回来就是满屏「在吗」。

现在多了一个**每日上限**：

| 设置项 | 在哪 | 说明 |
|---|---|---|
| 每日上限 | 聊天设置 →「记忆与后台」→「后台消息」 | 单个联系人 |
| 每日上限 | 设置 →「默认值」→「后台消息」 | 所有联系人的默认值 |

- `0` = **不限**（升级后的默认值，行为与你升级前一模一样）
- 上限按**本地日期**跨天自动归零
- 与已有的间隔限制**叠加**生效：两个条件都满足才会发
- 静默时段管的是「几点发」，每日上限管的是「一天几条」，两者互不替代

> 出处：`js1/miya-chat-background.js` 的 `withinDailyCap()` / `localDayKey()`，
> 字段定义在 `js1/miya-chat-store.js` 的 `backgroundMessage`（`maxPerDay` /
> `dayKey` / `dayCount`）。
>
> 计数只在**消息真的发出去之后**才 +1 —— 生成失败、接口没配、被忙线挡掉
> 都不占当天的额度。

### 4.2 角色会在你打字时插嘴吗？

**不会。** 你正在输入框里写字时，主动消息会自动跳过这一轮，
等你写完（输入框清空）自然恢复。

判定不看具体是哪个输入框（有 `xw-writer-input`、`qq-room-input` 等多个），
而是按「焦点元素是不是可输入的 + 里面有没有实际内容」。所以：

- 点了一下输入框但没打字 → 不算在写，**不会**压制
- 输入框里只有空格/换行 → 同样不算
- `contenteditable` 区域里写了字 → 算

> 出处：`js1/miya-chat-background.js` 的 `isUserComposing()`。
>
> 这是「跳过」不是「失败」：被跳过的这一轮不会记进失败冷却，
> 也不会消耗每日额度。

## 五、部署形态

### 5.1 登录页面在开源版里看不到

`index.html` 引用了 `miya-auth/config.js`、`boot.js`、`auth.js`，
但**开源版没有 `miya-auth/` 这个文件夹**。

**这是刻意的**：登录包只在部署版上传，开源版直接跳过。
控制台可能看到这三个文件 404 —— **可以忽略**。

> 出处：`index.html` 第 62 行的注释「登录包：仅部署版上传 miya-auth/ 时生效；
> 开源版无此文件夹则跳过登录」。

### 5.2 换设备后配置不会自动跟过去

所有数据都在**当前浏览器**里（localStorage + IndexedDB），
换浏览器 / 换设备 / 清浏览器数据 = 数据不随之迁移。

**怎么做**：用「配置导出」把设置导出成 JSON，在新设备导入。
**注意**：聊天记录与图片体积大，通常不在导出范围内，需要单独备份。

## 六、会看到但可以忽略的提示

以下提示都是**设计好的兜底**，出现时按提示操作即可，不是崩溃：

| 提示文字 | 含义 | 该怎么做 |
|---|---|---|
| `上下文用量计算失败，请刷新后重试` | 计数逻辑遇到异常数据 | 刷新 |
| `世界书加载失败，请刷新后重试` | 世界书未就绪就调用了 | 刷新 |
| `压缩组件未加载，请刷新页面后重试` | 懒加载脚本还没到位 | 刷新 |
| `存储未就绪，请稍后重试` | IndexedDB 还在打开中 | 等 1~2 秒重试 |
| `对方暂时没有回应，可再试一次` | 模型侧超时或空返回 | 重试一次 |
| `导入失败：处理时遇到意外错误，请重试（若反复出现可反馈此文件）` | 导入链路遇到未预期错误 | 重试；**反复出现请把这个文件反馈给我** |
| `导入失败：写入后界面刷新出错，已撤销本次导入` | 写库成功但渲染炸了，**已自动回滚** | 重试；反复出现请反馈 |

> 最后两条是 2026-09 那两轮修复专门加的：**失败时会真的撤销**，
> 不会留下「列表里多一条但点不进去」的脏记录。

## 七、排查工具（遇到怪问题先用这个）

如果某个现象不属于上面任何一条，**别猜，直接看诊断**：

### 方式一：屏幕诊断面板（手机上用这个）

1. 地址栏在网址后加 `?miya_debug=1`，回车；
2. 控制台执行 `miyaDiag.show()` —— 诊断会**画在屏幕上**，可长按复制。

> 为什么要做到屏幕上：**手机浏览器没有开发者工具**。
> 之前有好几个问题就是因为「用户没法提供控制台信息」而白白多花了两轮。

### 方式二：开启详细日志

| 开法 | 适用 |
|---|---|
| 网址后加 `?miya_debug=1` | 临时看一眼 |
| 控制台 `miyaDiag.enable()` | 本次会话 |
| `localStorage.setItem('miya-debug','1')` | 持久开启（记得 `miyaDiag.disable()` 关掉） |

### 方式三：导出诊断记录

```js
miyaDiag.dump()      // 最近 200 条记录（含异常、存储失败）
```

## 八、开发时怎么跑测试（别一上来就跑全量）

> 这一节是给**改代码的人**看的。只想用 App 的话可以跳过。

### 8.1 四个模式，按需选

```bash
python3 test/run-all.py --list           # 先看有哪些脚本（瞬间）
python3 test/run-all.py --filter api     # 只跑文件名含 api 的
python3 test/run-all.py --fast           # 只跑不用服务的（秒级）
python3 test/run-all.py                  # 全量（约 27 分钟）
```

**关键：`--filter` 才是日常主力，全量只在发版前跑一次。**

### 8.2 选模式的判据：改动面广 ≠ 该跑全量

改了几个文件，就找**覆盖这几个文件的脚本**去跑，而不是无脑全量。

举例 —— 改 `js2/miya-api-bridge.js`：

```bash
python3 test/run-all.py --filter api      # api_presets / api_model / api_preset 全中
python3 test/run-all.py --filter inject   # 注入链也走这条
python3 test/run-all.py --filter race     # 竞态
```

加起来几分钟，覆盖率却不比全量差。**全量的真正价值是「发现意外波及其他模块」**，
而这件事更应该靠**判断依赖关系**解决，不是靠等 27 分钟。

> ⚠️ 常见误区：觉得「改动多 → 保险起见跑全量」。
> 全量慢 27 分钟，且输出极长；跑多了人就不看了 —— 反而更危险。

### 8.3 让输出看得见

| 场景 | 写法 |
|---|---|
| `--filter` / `--fast`（秒级） | **直接前台跑**，输出短、看得见 |
| 全量（27 分钟） | 用 `tee` 落盘：`python3 test/run-all.py 2>&1 \| tee /tmp/r.log` |

**别用 `\| tail -45`** —— 它会把输出全堵在管道里，
中间过程一个字都看不到，只能干等（这是踩过的坑）。
**也别把长任务塞后台** —— 输出进日志文件，界面上同样是黑箱。

### 8.4 静态检查：ESLint no-undef

```bash
npm run lint                  # 全量静态检查
python3 test/lint_undef.py    # 同样的事，走统一入口
python3 test/run-all.py --filter lint   # 已被 run-all 收录
```

专抓一类问题：**「跑起来才崩」的未定义引用**。

例如 `trim is not defined`、`invalidateApiPresetsCache()` 全文件未定义、
`state.chatId = chatId`（`chatId` 根本不存在）—— 都属于这一类：
代码能加载、平时不报错，**点到某个按钮才 `ReferenceError`**。

`lint_undef.py` 已作为**静态脚本**接进 `run-all.py`（5 断言 / 约 2.5s），
`--fast` 和全量都会自动带上。

发现问题的处理记录见 `docs/ESLint基线与未定义引用清单.md`。

## 九、反馈问题时请附上

能大幅缩短定位时间的材料，按价值排序：

1. **诊断记录**：`miyaDiag.dump()` 的输出，或诊断面板截图；
2. **复现步骤**：点哪里 → 看到什么 → 期望什么；
3. **设备与浏览器**：手机上尤其要说清是哪个浏览器；
4. **版本号**：控制台执行 `document.querySelector('meta[name="miya-sw-build"]').content`。

> 反过来，**「某个文件」如果能一起发过来，是最快的** ——
> 前面几轮的疑难问题（含 `trim is not defined` 那次）都是靠用户发来的
> 那个具体文件才定位到的。
