## 二、缺陷 1 —— 整桶注入文本丢失（核心）

### 现象

同一深度桶（前/中/后）里，只要存在一条 `globalReach='all'` 且 `key=['']` 的词条，
**该桶的注入文本会整段消失**，而同批词条仍出现在 `matched` 数组里 —— 面板显示「已命中」，
实际 prompt 里什么都没有。完全静默，无报错。

### 复现（真实浏览器 A/B 对照）

世界书放三条，`back` 桶：`e3`（全软件，`key=['']`）+ `e4`（普通词条，`key=['苹果']`，本轮命中）。

**修复前** —— `matched` 说命中了 `e4`，但 `text` 里没有它：

```
matched: ['e1', 'e2', 'e3', 'e4']
text: 【世界书·前·全局设定】
- 同桶陪衬: 这是陪衬内容          ← back 桶整段消失
```

**修复后**：

```
matched: ['e1', 'e2', 'e3', 'e4']
text: 【世界书·前·全局设定】
- 空关键词设定: 这是空关键词内容   ← back 桶回来了
- 同桶陪衬: 这是陪衬内容
```

### 根因

`js2/miya-worldbook-prompt.js` 中 `entryHasKeys()` 手写了一份判据，与 `matcher.entryKeywords()` **不等价**：

```js
// prompt.js（错误）
var k = Array.isArray(entry.key) && entry.key.length ? entry.key : (entry.keywords || []);
return Array.isArray(k) && k.length > 0;        // 只看数组长度，不剔空串

// matcher.js（权威）
if (Array.isArray(entry.key) && entry.key.length) return entry.key.filter(Boolean);  // 剔除空串
```

于是 `key=['']` 时两边结论相反：

- `prompt.js` 认为「**有关键词**」→ 丢进 `keywordPool` 参与关键词匹配 → 永远匹配不上 → 本轮被判不注入
- `matcher.js` 认为「**无关键词**」→ 走 `reach==='all'` 常驻分支直接放行

两条路都拿不到它，而 `buildWorldbookPrompt` 末尾又用 `merged` 去分桶，
于是 `buckets[该深度]` 为空，**同桶其它词条被一起吞掉**。

### 修复

统一到唯一判据，禁止各写一份：

```js
// matcher.js 新增，作为全链路唯一权威判据
function hasAnyKeywords(entry) {
  return entryKeywords(entry).length > 0;   // entryKeywords 已 filter(Boolean)
}

// prompt.js 改为委托，不再自己算
function entryHasKeys(entry) {
  if (matcher && typeof matcher.hasAnyKeywords === 'function') {
    return matcher.hasAnyKeywords(entry);
  }
  return false;
}
```

## 三、缺陷 2 —— 运算符优先级写错

`js2/miya-worldbook-matcher.js` 第 180 行附近：

```js
// 错误写法：|| 优先级低于 &&，实际等价于 (constant || 无关键词) ? true : stKeywordMatch()
return entry.constant || !(entry.key && entry.key.length) && !(entry.keywords && entry.keywords.length)
  ? true
  : stKeywordMatch();
```

`stKeywordMatch()` 内部走 `st.activateEntries`，对无关键词词条返回空数组 → `false`。
叠加旧判据后，`key=['']` 的全软件词条掉进这里被判负。

修复：补括号，并改用统一判据。

```js
return entry.constant || !hasAnyKeywords(entry)
  ? true
  : stKeywordMatch();
```

同时修掉同一函数局部分支里第三份不等价写法（`entry.key.length` 未剔空串）：

```js
// 局部词条：绑定角色后若「真的没有关键词」应常驻
if (bound.length && !entryKeywords(entry).length) return true;
```

## 四、缺陷 3 —— 新建片段默认状态导致永久不注入

### 现象

用户点「新建片段」→ 填名字和正文 → 保存。词条**永远不会出现在任何 prompt 里**，且 UI 不给任何提示。

### 根因

`js2/miya-worldbook-app.js` 新建片段时 `data` 对象**没有 `constant` 字段**：

```js
var data = entry || {
  scope: ..., globalReach: 'online_offline', depth: 'middle',
  keywords: [], boundRoleIds: [], enabled: true,
  // ← 无 constant
};
...
if (data.enabled === false) statusEl.value = 'disabled';
else if (data.constant) statusEl.value = 'constant';
else statusEl.value = 'normal';          // ← undefined 落在这里 → 下拉显示「关键词触发」
```

保存时：

```js
constant: status === 'constant',   // false
keywords: [],                       // 用户没填（UI 也没说必须填）
```

→ `matchEntry` 走 `reach='online_offline'` 分支 → `stKeywordMatch()` → **`no_keywords` 拒绝**。

`explainEntry` 的诊断原文：

```
reason: no_keywords
detail: 该词条非常驻，但没有配置任何关键词，永远不会被触发
```

更微妙的是 `index.html` 里状态下拉的**第一项是「常驻」**，视觉上看起来默认就是常驻，
但代码的 `else` 分支把它覆盖成了「关键词触发」—— **UI 与代码默认值不一致**。

### 修复

在新建片段的对象里显式声明默认值，与下拉第一项对齐：

```js
enabled: true,
/* ⚠️ 新建片段默认「常驻」。缺省会让 statusEl 落进 else 分支显示「关键词触发」，
   而用户新建时通常不会填关键词，于是被 no_keywords 拒绝，词条永远不注入且毫无提示。 */
constant: true,
```

> **行为变更提示**：修复后「新建片段」默认状态为**常驻**，创建即生效。
> 若此前有依赖旧默认值的既有数据 —— 不受影响，旧数据 `constant` 字段已被 store 归一化为 `false`，
> 只是这些词条本来就一直不生效。需要它们生效的话，手动把状态改成「常驻」或补上关键词。

## 五、未改动 / 澄清项

调查中确认以下行为**是设计意图，不是缺陷**，未做改动：

- **无关键词 + 非常驻的普通全局词条不注入**：`no_keywords` 拒绝是有意设计，
  避免「没配触发条件的词条无条件污染所有 prompt」。
- **`scope='local'` 且未绑定角色时不注入**：`roleMatches` 在 `bound` 为空时返回 `true`（不限角色），

  本次未改，留作后续。
- **`key=[' ']`（纯空白）**：`entryKeywords` 只做 `filter(Boolean)`，不过滤纯空白串。
  已统一到该函数，行为一致；是否需要更激进的 trim 过滤属产品决策。

# 第二批：对话 API 预设保存

## 八、缺陷：保存预设后，返回再进来就没了

### 现象

用户在「对话 API → 接口预设」里点 ✓ 保存：

1. toast 提示「预设已保存」✓
2. 当前面板的下拉里确实出现了新预设 ✓
3. **返回上一级、或切走再回来 → 下拉变空了** ✗
4. 整页刷新后同样是空的 ✗

用户感知就是「保存预设后发现没保存到」。**数据其实一直好好躺在 IndexedDB / localStorage 里** ——
丢的是渲染用的那份列表。

### 复现（真实浏览器，走完整 UI 流程）

```
先进面板（此时预设为空）  → 下拉 ['']                              
点 ✓ 保存「竞态预设」      → 下拉 ['', '竞态预设']   看起来成功了
查盘                      → ['竞态预设']            数据确实在
返回 → 重进面板            → 下拉 ['']               ✗ 预设不见了
```

### 根因：`ensureReady()` 返回的是「首轮快照」，被拿去重绘

`js2/miya-api-config.js` 的 `ensureApiPresetsReady()` 返回一个**只 resolve 一次**的 promise，
闭包里捕获的是**首次加载时的那个数组对象**：

```js
apiPresetsReady = loadApiPresetsArr().then(function (list) {
  if (!Array.isArray(apiPresetsCache)) apiPresetsCache = list.slice();
  return apiPresetsCache;      // ← 首次加载的对象，之后永远不再变
});
```

而 `upsert()` 每次都是 `apiPresetsCache = list.slice()` —— **换了新对象**，老 promise 仍指向旧的
（首次进入时为空的那个）数组。于是必经路径必然踩坑：

```
先进面板（预设为空，promise 固化为 []）
  → 保存一条（apiPresetsCache 换成新的非空数组，promise 不变）
  → 返回再进 → hydrateApiPresets 拿 ensureReady() 的返回值重绘
  → 拿到首轮的 []，把正确的下拉覆盖成空
```

实测打桩输出，一眼可见两处数据不一致：

```
getCached()   → ['追踪预设']    ← 内存缓存是对的
ensureReady() → []              ← 仍是首轮快照
```

**同一个 bug 在这个模块里已经复发过三次**，每次都是「拿 `ensureReady()` 的返回值当数据用」：

| 次序 | 位置 | 状态 |
|------|------|------|
| 1 | `upsert` / `remove` | 已修（改走 `enqueueApiPresets` 串行队列） |
| 2 | `find` | 已修（`ensureReady().then` 里重新读 `apiPresetsCache`，注释写明了原因） |
| 3 | **`hydrateApiPresets`** | **本次修复** |

### 修复

**数据层** —— `ensureReady()` 已就绪时 resolve **当前**缓存，不再吐旧快照：

```js
function ensureApiPresetsReady() {
  if (apiPresetsReady) {
    /* 已就绪：直接返回「此刻」的缓存，而不是当初那个快照 */
    return Promise.resolve(apiPresetsCache || []);
  }
  ...
}
```

**UI 层** —— `hydrateApiPresets` 显式再读一次 `getCached()`，双保险，也让意图清楚：

```js
Promise.resolve(ready).then(function () {
  if (!presetPickEl()) return;
  /* ★ 必须重新读 getCached()，不能用 ensureReady() 的返回值 */
  var list = mod.getCached ? mod.getCached() : null;
  refreshApiPresetOptions(list || []);
}).catch(function () {});
```

### A/B 对照

回滚这两处修复后跑新增回归测试：**4 项失败**，且失败项正是核心场景：

```
· 返回后重进，预设仍在（曾经的失败点）   ✗
· 四条预设全部保留                       ✗
· 已删除的不再出现                       ✗
· 落盘列表与下拉一致                     ✗
```

修复后 14/14 全通过。

# 第三批：切换预设后点保存，却又变回切换之前

## 十、缺陷：切换预设后点保存，配置被回退

### 现象（用户原话）

> 「我切换了对话 api 的预设，结果一点保存，却没切换成功，
>   变回来切换之前的 URL 和 key。」

注意现象里的关键词：**「变回来切换之前的」**。这不是"没保存"，而是**保存把旧值又写了一遍**。

### 复现

用界面真实操作，正式配置为「线路A」，再存一条「线路B」：

| 步骤 | 正式配置 | 表单显示 |
|---|---|---|
| 1. 下拉切到线路B | A | **B** ← 只活在 DOM 里 |
| 2. 点返回（或切别的子视图） | A | 节点被销毁，**B 丢失** |
| 3. 再进来 | A | **A** ← 从正式配置重绘 |
| 4. 点保存 | **A** | 保存的是 A |

### 根因

三个环节缺一不可，所以这个 bug 很绕、也很容易只修一半：

**① 「载入预设」按设计只改 DOM，不动正式配置**

`applyApiPresetToForm()` 的注释写得很清楚：载入是一次**可反悔的预览**，用户随后点「保存」才生效。
所以切换后的线路**只活在 DOM 里**。

**② 多处路径会整块重绘，把 DOM 里的值销毁**

`render()` 对子视图是 `body.innerHTML = renderSubView(...)` —— **整块换掉**。而这些路径都会触发它：

- `closeSubView()` —— 点返回
- `openSubView()` —— 切到别的子视图 / 再进来
- `open()` 链里的异步 `scheduleRender()` —— **用户不动界面也会触发**

**③ 重绘时的初值取自「正式配置」**

```js
function renderApiChatSub() {
  var cfg = (global.miyaGetApiConfigCached && global.miyaGetApiConfigCached()) || {};
  // ...
  '<input ... id="mq-api-base" value="' + esc(cfg.baseUrl || '') + '">'
```

正式配置在点保存前不会变，所以重绘出来的一律是**切换前的旧线路**。

三者叠加：切换 → 重绘丢值 → 从旧值重绘 → 保存写回旧值。**全程零提示，因为每一步都"成功"了。**

---

### 修复过程：我第一版修错了方向

这一节如实记录一次**返工**，因为结论对后续维护很重要。

#### 第一版（错误）：给中间态打补丁

我按「返回 = 未保存编辑应当存活」的直觉，引入**子视图表单草稿** `state.subViewDraft`，
配套 `SUB_VIEW_DRAFT_FIELDS` 字段表与 `captureSubViewDraft` / `applySubViewDraft` /
`setSubViewDraftField` / `clearSubViewDraft` 四个函数，在 `render()` 换 innerHTML 前后抓取、回填。

测试 16/16 通过。**但这是给一个多余的设计打补丁。**

#### 用户第二轮反馈：出现了新症状

> 「还是不行啊 而且一点保存 保存的预设都没了 但是重进又会显示出来」

这是我改动**引入的副作用**：`applySubViewDraft` 拿草稿里的 `__presetName` / `__presetPick`
回填下拉框，与重绘后重建 `<option>` 的时序错位，把列表刷成空。
**数据在磁盘里没丢**（所以"重进又会显示出来"），只是 DOM 被刷没了。

#### 真正的根因：迁移时凭空造出了一个中间态

用户随后提供了旧包 `karinn-imagegen-v5-细线图标版`，并说明：

> 「以前对话 api 设置是好的，但是后来把这个功能移过来的时候漏了预设功能，又重新补了。」

拿旧包做基线 diff，关键差异一目了然 —— **旧包的预设选中就直接写正式配置，压根没有中间态**：

```js
// 旧包 js2/miya-settings-app.js
presetPick.addEventListener('change', function () {
  var name = presetPick.value;
  if (!name) return;
  ensureApiPresetsReady().then(function (list) {
    var pr = (list || []).filter(function (x) { return x && x.name === name; })[0];
    if (!pr || !pr.config) { toast('未找到该预设'); return; }
    setApiConfig(pr.config);          // ← 选中即刻写正式配置，一步到位
    syncFormsFromConfig();
    persistSystemPrefs();
    toast('已载入「' + name + '」');
  });
});
```

另外旧包还做过两件被漏掉的事：预设里存的是**整份 config**（`{ name, config, savedAt }`），
以及温度滑块的数值标签联动（`syncTempLabel`）—— 拖滑块只有条动、数字不动。

所以：**「载入 = 预览、点保存才生效」这个中间态是迁移时新造的，不是原有设计。**
它凭空制造了「只活在 DOM 里的值」，再叠加 `render()` 的整块重绘，才长出这一串 bug。
第一版的草稿补丁正是在为这个多余设计兜底 —— 属于治标，且自身引入了新缺陷。

### 最终修复：对齐旧包，选中即生效

撤销全部草稿机制，把 `loadApiPresetFromPick()` 改成一步到位：

```js
function loadApiPresetFromPick() {
  var mod = global.miyaApiPresets;
  var pick = presetPickEl();
  var name = pick ? String(pick.value || '').trim() : '';
  if (!mod || !name) return;
  mod.find(name).then(function (p) {
    if (!p) { toast('预设不存在'); return; }
    /* 写进正式配置并落盘 —— 这一步是「立即生效」的全部含义 */
    if (typeof global.miyaSetApiConfig === 'function') {
      global.miyaSetApiConfig(presetToConfigPatch(p));
    }
    applyApiPresetToForm(p);
    syncTempLabel('#mq-api-temp', '#mq-api-temp-lbl');
    syncTempLabel('#mq-api2-temp', '#mq-api2-temp-lbl');
    var nameEl = pageEl && pageEl.querySelector('#mq-api-preset-name');
    if (nameEl) nameEl.value = name;
    toast('已载入：' + name);
  }).catch(function () { toast('载入失败'); });
}
```

配合一个字段映射函数，保证「保存预设」写进去的形状与「载入预设」读出来的形状永远对称：

```js
function presetToConfigPatch(p) {
  if (!p) return {};
  var out = {};
  if (p.baseUrl != null) out.baseUrl = String(p.baseUrl);
  if (p.apiKey != null) out.apiKey = String(p.apiKey);
  if (p.model != null) out.model = String(p.model);
  if (p.temperature != null) out.temperature = p.temperature;
  if (p.fallbackBaseUrl != null) out.fallbackBaseUrl = String(p.fallbackBaseUrl);
  if (p.fallbackApiKey != null) out.fallbackApiKey = String(p.fallbackApiKey);
  if (p.fallbackModel != null) out.fallbackModel = String(p.fallbackModel);
  if (p.fallbackTemperature != null) out.fallbackTemperature = p.fallbackTemperature;
  out.fallbackEnabled = !!p.fallbackEnabled;
  return out;
}
```

同时把旧包有、迁移时丢掉的**温度标签联动**补回来（载入预设是直接写 `input.value`，
不触发 `input` 事件，标签不会自己更新）：

```js
function syncTempLabel(rangeSel, labelSel) {
  if (!pageEl) return;
  var r = pageEl.querySelector(rangeSel);
  var l = pageEl.querySelector(labelSel);
  if (r && l) l.textContent = String(r.value);
}
```

**核心思路**：不要跟 `render()` 的整块重绘对抗 —— 只要「载入」这一步就把值写进**唯一的真源**
（正式配置 + 落盘 + 缓存），此后无论重绘多少次、从哪条路径重绘，读到的都是同一份正确数据。
没有中间态，就没有"中间态丢失"这一类 bug。

## 十一、缺陷：点顶部「保存」后，预设下拉整个变空

上一批改完（选中即生效）后用户又报了一次，而且这次描述得很具体：

> 「主线路保存成功了 但是点保存后 已存的预设还是会不见啊？
>   如果我还想换预设 又得重进才能看到预设」

### 定位过程：我连续三次没复现出来

值得记录，因为**我的测试一直在骗我**。

第一轮：我按"点保存"理解为**子视图表单底部那个保存按钮**
（`data-mq-set-sub-save="api-chat"`）。跑下来一切正常，下拉、内存、磁盘全对。

第二轮：我加上了"选中预设 → 保存"的完整链路，还是正常。

第三轮：我连"返回再重进"的循环都模拟了，依然正常。

三次都绿，但用户三次都说不正常。于是我停下来问了一句 ——
原来是**我一直在测错按钮**：

| 我问 | 用户答 |
|---|---|
| 点的是哪个保存？ | **顶部导航栏右侧那个**（根列表页就有） |
| 预设怎么个不见法？ | **下拉列表整个空了**（只剩「选择已存预设」） |
| 怎么重进？ | 点返回退出子页，再点进来 |

改用**顶部导航栏的保存**（`data-mq-set-save`）后，一次性复现：

```
存完两条预设      : opts = ["", "线路A", "线路B"]
点顶部「保存」    : opts = [""]              ← 列表被清空
                    pickVal = ""             ← 选中项也没了
                    （此后永不恢复）
内存 / 磁盘       : ['线路A', '线路B']        ← 数据完好
```

数据没丢 —— 这正好解释了用户那句「重进又会显示出来」。

### 根因：`render()` 的子视图分支重建了 DOM，却没有补 hydrate

`render()` 里这段（修改前）：

```js
if (state.subView) {
  var titleEl = pageEl.querySelector('.st-navtitle');
  if (titleEl) titleEl.textContent = SUB_VIEW_TITLES[state.subView] || '聊天设置';
  body.innerHTML = renderSubView(state.subView);   // ← 换了一副新骨架
  body.scrollTop = 0;
  return;                                          // ← 直接返回
}
```

`renderSubView()` 吐出的只是**静态骨架** —— 预设下拉此刻只有一条占位项
`<option value="">选择已存预设</option>`，真正的选项要靠 `hydrateApiPresets()`
异步从缓存/磁盘读出来再填进去。

而顶部「保存」的调用链恰好是：

```
saveForm()                              // 第 2079 行
  → scheduleRender({ fromStore: true })
    → render()
      → state.subView 为真 → 换 innerHTML → return   ← 没有 hydrate
```

于是下拉被打回空骨架，**且此后没有任何机制再把它填回来**。
「重进」之所以正常，是因为那条路走的是 `openSubView()` → `scheduleSubViewHydrate()`，
它本来就会补 hydrate。

> 这里其实早有伏笔：`applySubViewHydrate` 的注释里已经写了
> 「api-chat → 下拉框看似存着预设，进去却是空的」—— 同一个病，
> 只是那次只修了"进来时"这一条路径，漏了"重绘时"这条。

顺带第二个问题：即便 hydrate 补上了列表，**选中项也保不住** ——
`refreshApiPresetOptions()` 用 `pick.value` 当"当前选中"，而重绘换出来的
新 `<select>` 的 `value` 天生是空的，于是永远回落到占位项。

### 修复

**① 重绘后补一次 hydrate**

```js
if (state.subView) {
  var titleEl = pageEl.querySelector('.st-navtitle');
  if (titleEl) titleEl.textContent = SUB_VIEW_TITLES[state.subView] || '聊天设置';
  body.innerHTML = renderSubView(state.subView);
  body.scrollTop = 0;
  /* ★ 重绘之后必须补一次 hydrate */
  applySubViewHydrate(state.subView);
  return;
}
```

直接同步调用，不排 rAF —— 重绘刚在本帧同步完成，节点就是新的那一批；
`applySubViewHydrate` 本身幂等，内部各自校验节点存在。

**② 让选中项跨重绘留存**

`state` 增加一个 `apiPresetPick`，`refreshApiPresetOptions()` 按可信度取两个来源：

```js
var current = pick.value || state.apiPresetPick || '';
```

`pick.value`（用户刚手动选的，最新）优先，取不到再回落到记住的值。
写入点：下拉 change、保存预设成功、载入预设。
清空点：删除预设、关闭设置页（`close()`）、切换 chatId（`open()`）——
后两处与 `formDraft` 的处理保持一致，避免把 A 会话选中的预设名带到 B 会话。

1. **Service Worker 缓存**：`sw.js` 对静态资源是 networkFirst，但离线/

2. **解压目录错位**：多次下载解压出现多个目录，浏览器书签/历史仍指向旧目录。

**用户一句"以前改完代码的新包一直用同样方法更新"直接点破了根因**：
原作者每次发版都 bump 两处 —— `index.html` 里改过的 `<script>` 引用
带 `?v=N` 参数，`sw.js` 里 `var CACHE = 'miya-vN-karin'`。我修了文件

|---|---|---|

**这是发布流程的一步，不是代码缺陷** —— 但漏掉它，再正确的代码也到不了
用户浏览器。此后发版务必同步 bump 这两处。

同时补了第三层防御 —— `renderApiChatSub()` 渲染时就**同步**带上缓存里已有的
预设选项（`apiPresetOptionsHtml()`，选中项一并按 `state.apiPresetPick`

| 层 | 时机 | 保障 |
|---|---|---|
| ① 渲染同步带选项 | 换 innerHTML 的同一帧 | 下拉**永不空**（哪怕某条路径漏了 hydrate） |
| ② render 后补 hydrate | 重绘同步完成之后 | 数据从缓存/磁盘刷新到最新 |
| ③ apiPresetPick 记忆 | 跨重绘 | 选中项不丢 |

**架构考古（旧包基线确认）**：对照 `karinn-imagegen-v5` 发现，旧包的对话
API 面板 `#miya-st-panel-chat` 与预设下拉 `#miya-st-preset-pick` 是**写死在
index.html 里的静态节点**，整个生命周期从不重建 —— 保存只调
`syncFormsFromConfig()`，根本不碰下拉，所以旧包「没有这个问题」不是设计
精妙，而是**预设下拉住在一间永远不会被拆的房子里**。后来把三个设置功能
合并进聊天设置页，API 表单变成 `renderSubView()` 动态生成的字符串、随
`render()` 整块重建 —— 预设消失的病根正是这次搬迁：**房子从「不拆」变成
「每次保存都拆了重盖」，但家具（下拉选项）没跟着搬进图纸（renderSubView
的静态骨架）里**。补预设功能时又没意识到这个环境差异，才连环踩坑。

# 第五批：线下「重发生成内容一模一样、改完好几天又复发」根治

## 十五、症状与误判

用户反馈（原话精炼）：

> 关于线下功能点重发键，角色层重新生成的内容还是一模一样的，
> 改了很多次，两次改完好像改好了，过了一两天又会出现。

**第一直觉会去查重发逻辑**——但前几批已经把重发链路修得相当完整（见
`regenerateAppointment` / `buildRegenerateHintBlock` / `regenCount`）：
软删本轮 assistant → `attempt = regenCount + 1` → hintBlock 插在当前 user 前
（明确告诉模型「这是第 N 次重答、严禁复用上一版措辞」）→ `keepRegenCandidate: false`
不产候选 → payload 不带 seed → 请求纯网络无本地缓存。全链路自洽，沙箱里 11 套测试全绿。

**但这解释不了「过一两天又出现」**。纯逻辑 bug 不会间歇自愈——
「改完好、隔几天复发」的时间特征，恰恰是**用户浏览器某些时刻跑的根本不是这份新代码**。

## 十六、真正的通道：Service Worker 让旧代码间歇复活

`sw.js` 里有两处「旧代码复活」的设计通道，恰好对应症状的两面：

### 通道 ① `matchIgnoringVersion` 兜底喂任意旧副本

旧版 `networkFirst` 离线回退时按「路径」遍历缓存里**任意 `?v=` 的副本**，注释自己写着：

> 版本号更新时宁可先用一份稍旧的实现把界面跑起来，也好过整份脚本消失。

对显示类代码可接受，**对逻辑修复就是旧 bug 复活**：
某次网络抖动/离线打开 → 回退命中 `?v=80` 的旧 `miya-appointment-app.js`
（attempt 恒为 1、无 hintBlock）→ 重发时每轮 prompt 逐字节相同 →
模型收敛/网关 prompt cache 命中 → 「一模一样」。网络恢复后又是新代码 →「又好了」。
**这正是一两天后间歇复现的机制**。

### 通道 ② `?v=` 漏 bump + HTTP 缓存旧响应

第三批考古已实锤过一次：原作者发版每次 bump `index.html` 的 `?v=` 与 `sw.js` 的
`CACHE` 号；漏 bump 时「浏览器/SW 理所当然继续喂旧副本」。更深一层：
SW 的 `fetch(request)` 不带 `cache:` 选项 → **命中浏览器 HTTP 层的新鲜旧响应**
（静态托管对 JS 发 `max-age` 长缓存）→ 旧内容被当「网络成功」吞进 SW 缓存。
?v= 漏 bump 时这条通道尤其致命——新文件躺在磁盘上，SW 永远拿不到。

### 通道 ③ SW 更新交替期 / 壳浏览器冻结旧页面

`skipWaiting + clients.claim` 后，已加载旧 JS 的页面仍跑旧代码直到下次刷新；
某些壳浏览器（如 Via）后台冻结的旧页面，过一两天切回来仍在跑旧逻辑。
docs 第三批已经踩过 Via 这类壳浏览器的坑。

## 十七、根治方案

核心一句话：**让「旧版本副本」在缓存里结构性消失**。

### ① cache key 归一化（sw.js）

所有 `put` / `match` 一律走「去查询串、目录路径补 `index.html`」的归一 key：

```js
function normalizeCacheUrl(url) {
  var u = new URL(url); u.search = '';
  var p = u.pathname || '/';
  if (p.charAt(p.length - 1) === '/') u.pathname = p + 'index.html';
  return u.toString();
}
```

效果：
- 每个资源路径在缓存里**永远只有一份副本**，等于「最后一次在线成功获取的版本」；
- `/?source=pwa`（PWA 启动 URL）与 `/`、`/index.html` 归一为同一 key，
  三处入口共享同一份最新副本（见场景 B）；
- `?v=` 参数从此只是绕过 HTTP 缓存的加速手段，**不再是正确性依赖**
  （漏 bump 也不会喂旧代码）。
- 删掉 `matchIgnoringVersion` 的「任意版本兜底」—— key 归一后精确匹配必中，
  旧版本回退结构性消失。

### ② networkFirst 加 `cache: 'no-cache'`（sw.js）

```js
return fetch(request, { cache: 'no-cache' }).then(function (res) { ... })
```

强制每次向服务器协商验证（`If-Modified-Since`）。200 = 真新内容（put 覆盖同 key），
304 = 与服务器一致。堵死「SW fetch 命中 HTTP 层新鲜旧响应」这条通道。

### ③ activate 清带参 key + 版本哨兵广播（sw.js）

- activate 时删除当前 CACHE 里**带查询串的旧格式 key**（上一版 SW 拋留）；
- `clients.claim()` 后向所有窗口 `postMessage({ type:'miya-sw-build', build: BUILD, cache: CACHE })`；
- 新增 `message` 事件响应「页面主动询问」—— 防广播早于本页注册监听而错过。

### ④ 版本哨兵监听（app.js + index.html）

- `index.html` 埋 `<meta name="miya-sw-build" content="sw-2">`；
- `app.js` 收到 SW 广播的 build 后与 meta 比对：**SW 比页面新才 reload 一次**
  （方向判断防镜像场景：SW 旧于页面时刷新反而可能在离线时回退到旧缓存页）；
- `sessionStorage` 标记防循环——一次会话最多自动刷新一次。
- 兜住「磁盘已是新版、当前页面还捧着旧副本」的窗口期（含壳浏览器冻结旧页面）。

# 第六批：切换模型保存不了（预设问题的同族第三个成员）

## 二十、症状（用户原话）

> 「对话 api 设置里的预设现在虽然能切换了，但是我切换模型，
>   却也出现了保存不了的问题。」

预设切换已修好（第三批），**切换模型**沿用了同一套病根的另一半：
预设下拉有三层防御，**模型下拉一层都没有** —— 模型列表与选中值只活在 DOM 里。

## 二十一、根因：四个缺陷叠加

### 缺陷 A（主犯）：模型缓存从未写入过 —— 调用参数形状错位

`fetchChatModels()` 里读/写缓存的调用与导出函数**签名不一致**：

```js
// 导出的接口（miya-api-config.js）
read(base, key)              // 内部自己算分桶
write(base, key, ids)

// 实际调用（错）
cache.read(cache.bucket(base, key))          // 把桶串当 base 传进去
cache.write(cache.bucket(base, key), ids)    // base=桶串、key=ids、ids=undefined
```

`write` 侧第三个参数（真正的 ids）是 `undefined`，`if (!ids) return` 直接退出 ——
**每一次点 ⟳ 都没有写缓存**。`read` 侧把桶串再当 URL 归一化一次，会拼出
`…/v1|aaaa/v1` 这种废 key，永远读不到。

于是「模型列表缓存」模块（注释里写明「下次进来能先出缓存，不必再点一次 ⟳」）
自诞生起就是**死代码**：列表只活在 DOM 里，任何一次 `render()` 整块换 innerHTML
（点顶部「保存」、open() 异步链、返回再进）都会把拉到的列表和用户切换的选中值
一起抹掉，下拉退化成「只剩当前生效模型一个 option」。用户接着点保存 →
**写回的是旧模型** —— 与预设当年「切换后保存被回退」一模一样的体感。

### 缺陷 B：`<select>` 赋值静默失败 → 保存把模型清空

`applyApiPresetToForm()` 的 `set('#mq-api-model', p.model)`：下拉 options 里没有
该模型（用户没拉过列表时必然没有）时，`el.value = v` 被浏览器静默置空。
用户随后点「保存」→ 表单快照读出 `model: ''` 写进配置 —— 把预设
「选中即生效」刚写好的模型**当场清空**。

### 缺陷 C：拉列表把当前模型打回空

`fetchChatModels.applyOptions()` 里 `selEl.value = ids.indexOf(current) >= 0 ? current : ''`
—— 当前模型不在 /models 返回列表里时被退回占位项（空值），点一次 ⟳
已选好的模型就没了，再点保存同样清空。

### 缺陷 D：副线路的缓存桶按「正式配置」找，找不到用户手填的线路

用户在副线路手填网关/密钥 → 点 ⟳ 拉列表（缓存按表单值分桶）→ 未保存时
触发重绘 → 渲染层按 `cfg.fallbackBaseUrl`（仍是空）找桶 → 落空，列表丢。

## 二十二、修复

对齐预设下拉的「三层防御」，外加 select 保值与调用形状修正：

| 层 | 位置 | 内容 |
|---|---|---|
| ① 渲染同步带列表 | `modelSelectHtml()` | 渲染时就从 `miyaApiModelCache` 读出该线路的列表画成 options（同步读 localStorage，不闪空）；桶键优先用**重绘前的旧表单值**（修缺陷 D），无缓存时维持原版单 option 形态 |
| ② render 后补 hydrate | `hydrateChatModelOptions()` | `applySubViewHydrate('api-chat')` 增加模型下拉回填（幂等，节点不在就跳过） |
| ③ 草稿跨重绘留存 | `state.apiModelPick / apiModel2Pick` | 下拉 change 时记录；**基线校验**：记录当时的 cfg.model 作基线，配置偏离基线（外部改配置）则草稿作废，防止把面板锁死；保存成功/载入预设时同步基线；`open()`/`close()` 清空 |
| ④ select 保值赋值 | `setSelectValueKeepingOption()` | option 不存在先追加再赋值（修缺陷 B）；`applyOptions` 当前值不在列表时追加保住而非退空（修缺陷 C） |
| ⑤ 缓存调用形状 | `fetchChatModels()` | `cache.read(base, key)` / `cache.write(base, key, ids)` —— 修缺陷 A，缓存从此真正写入 |

### A/B 对照（`test/api_model_switch.py`，33 项）

回滚 4 处修复（缓存调用形状、渲染带列表/草稿、预设载入保值）后：

```

✗ ★ 子视图保存后 model 落盘 beta-pro —— 实际 alpha-mini           （保存写回旧模型）

```

### 覆盖路径

| 场景 | 验证点 |
|------|--------|
| 1 核心 | 拉列表 → 切模型 → 顶部保存（重绘）→ 子视图保存，列表/选中/内存/磁盘四层一致 |

| 7 | 反向护栏：外部改 model，重进面板必须跟随（草稿基线校验） |
| 8 | 换会话不带未保存的模型草稿 |
| 9 | 全程无 JS 报错 |

## 二十九、UI-1：语音合成模型下拉是「死」的

- **清空聊天图片**：`deleteAllChatImages`，带确认框，明确「不可恢复」。

几百张图常驻引用会把内存吃满。按钮 `hidden` 由图片数量驱动。

## 三十一、顺带修掉的两个真 bug

### ① 字段误用：`list.length` vs `list.count`（我自己写进去的）

`collectChatMediaImages()` 返回的是 `{ items, totalBytes, count }` ——
**没有 `length` 字段**。我在新写的判断里写了 `if (!list || !list.length)`，
`undefined` 恒为假，于是**有图也永远走空态分支**。

这个 bug 很有代表性：`Array.prototype.length` 太顺手，以至于拿到一个
「长得像数组」的返回对象时会下意识写 `.length`。它不报错、不抛异常，
只是安静地走进错误分支 —— 和第六批那个「缓存读写调用形状错位」是同一类
**静默失败**。

> 门禁：所有跨模块返回结构，判断前先确认字段名；要么改成返回真数组，
> 要么在调用处显式用 `count`。

### ② 存储刷新写进「孤儿节点」（同族老坑）

`refreshStorageSub()` 原来是**同步拿节点引用、异步之后才写入**：

```js
var imagesEl = pageEl.querySelector('[data-mq-set-storage-images]');  // 同步拿
su.collect(true).then(function(){ ... imagesEl.innerHTML = ... });     // 异步写
```

`collect(true)` 是异步的（要扫 localStorage + 多个 IDB 库），耗时期间任何
一次重绘都会把子视图 DOM 整个换掉 —— 结果写进了已经脱离文档的旧节点，
表现就是**「点了重新扫描没反应」**。

修法：所有节点查询移进异步回调内部重新执行（两层异步各查一次），
并在回调开头复核 `state.subView === 'storage'`。

> 这和第六批「模型下拉列表只活在 DOM」是同一族：**凡是跨越异步边界的
> DOM 引用，都假设它已经失效。** 重绘是本项目的常态，不是例外。

## 三十二、UI-3：多选 JSON 备份被静默丢弃

**症状**：文件选择框开着 `multiple`，但 `importBackup` 对 JSON 只取
`jsons[0]`，其余**没有任何提示**。

**修法**：
- 多个 JSON → 仍只导入第一个（全量覆盖语义，多份互相覆盖没有意义），
  但 toast 明确「已选用第一个，其余 N 个被忽略」；
- ZIP + JSON 混选 → 只导 ZIP，并提示「JSON 请单独再导」——
  混选从来没有可定义的合并语义，但不能静默丢。

# 第十批 · 线下思维链「读到已删卷宗」

## 三十五、先排除了「删除失败」

第一直觉是「卷宗没删干净，被镜像或备份复活了」。写了
`test/audit_memory_ghost.py` 专门验证这条路径：

1. 建卷宗 → 写入绝密文本 → 加总结
2. 确认 `exportForMemory` 能读到（基线成立）
3. 走真实 `deleteSession` 全流程
4. 再次检查档案
5. 模拟重启（`invalidateCache` + `recoverSessionsFromChatMirrors` + `syncAllSessionsToChat`）

结果 **12/12 全绿**：

```

   {'sessionsAfterInvalidate': 0, 'exportedAfterSync': 0, 'hasSecret': False, 'recovered': None}

```

逐条排掉的相关链路：

| 链路 | 结论 |
|------|------|
| `purgeSessionOnlineMirrors` | 正确调用 `softDeleteChatMirror`，落 `{deleted:true, content:''}` —— 干净 |
| `filterTombstonedRecoveredByChat` | 确实按墓碑过滤，没漏 |
| `buildSessionFromMirrorMsgs` | 重建时 `summaryList: []` —— 总结无法被镜像恢复 |
| `mirrorMessageToChat` | 检查 `msg.deleted` / `isOpeningMessage` —— 已删消息不重新镜像 |

**结论：删除侧是干净的。「删不掉」不是根因。** 那么问题在**读取侧**。

## 三十六、真正的根因：记忆档案有三个来源，删卷宗只清了其中一个

线下思维链组装记忆时，总结来自**两个互不相干的存储**：

| 来源 | 存储位置 | 写入方 | `deleteSession` 会清它吗 |
|------|----------|--------|--------------------------|
| 线下卷宗总结 | `session.summaryList` | `MiyaAppointmentStore.replaceOrAddSummary` | ✅ 会 |
| 线上记忆总结 | `chatSettings.summaryList` | `MiyaChatSummary` 总结流程 | ❌ **不会** |
| 线上大总结 | `chatSettings.megaSummaryList` | 同上 | ❌ **不会** |

而线下剧情的总结在生成时，**往往会被同时写进这两处**。
于是出现了一个看似见鬼的现象：

> 用户删掉「往日卷宗」→ 卷宗列表空了、记忆表格（`miya-memory-tables-v1`）也空了 →
> 但当年写进 `chatSettings.summaryList` 的那份**同源副本仍在** →
> 线下思维链照旧把它整段读进来。

用户看到的「记忆档案里是我删过的卷宗里的内容」，**就是这份同源副本**。
它不是删除失败，是两套独立存储各管各的。

用 `test/audit_deleted_session_via_online_summary.py` 复现，一击即中：

```

2_删除线下卷宗后   {'offlineSessions': 0, 'onlineSummaries': 1, 'onlineStillHasSecret': True}
3_删除后 cross    {'summaryLen': 190, 'stillReadsSecret': True,
                   'onlineBlockCount': 1, 'offlineBlockCount': 0}
```

注入到 API 的原文：

```
【对话历史记忆·总结】
以下为线上与线下历史的压缩总结，请结合使用。

【长期记忆·对话总结】
【分镜1 · 消息1-4】
【绝密卷宗】我们约定过：小满最怕打雷，雷雨天要抱着她。   ← 卷宗已删，内容照旧在
```

**这就是用户报告的现象，稳定复现。**

## 三十七、顺带查出的两处注入缺陷

追这一条时，又发现注入侧本身有两个真问题。

### D1 世界书匹配上下文被喂了「总结」

`buildWorldbookContextText` 负责拼**世界书关键词匹配**的输入文本，原文案是：

```js
if (cross) {
    if (cross.summaryText) parts.push(String(cross.summaryText));   // ← 问题在这
    (cross.slotItems || []).forEach(...);
}
```

`summaryText` 由 `buildSummaryBlocksText` 用 `'\n\n'` join 而成 ——
块头 `【线下场景总结 · 会话xxx · 第a–b条】` 在拼接中丢掉了。
于是一整段「对旧剧情的压缩叙述」被拍成裸文本，
在匹配上下文里被当成**一条普通的、可能需要回应的消息**读。

两条后果：
1. **关键词误命中** —— 总结里满是名词，会把当年的世界书条目重新打亮；
2. **模型顺着旧剧情续写** —— 匹配上下文里的内容对模型而言是「上文」，
   它不会区分这是压缩叙述还是待接消息。

修复：世界书匹配只喂**时间线片段**（`slotItems`），不喂总结。
真正把总结送给模型的只有 `injectAppointmentCrossMemory` 一处，让它单独负责。

### D2 总结被双重套壳，且没有任何「这是历史」的定位

```js
apiMessages.push({
    role: 'system',
    content: '【对话历史记忆·总结】\n以下为线上与线下历史的压缩总结，请结合使用：\n\n' + sumText
});
```

而 `sumText` 自己已经带了抬头（`buildSummaryBlocksText` 拼的块头）。
更要紧的是这句壳**没有一句「这是已发生的历史、不是待接内容」的说明**，
且注入位置在 `systemContent` 之后、历史区（`historyStart`）之前 ——
正是提示前缀区、缓存命中的关键区。

修复后：

```
【对话历史记忆·总结】
以下为线上与线下历史的压缩总结，请结合使用。
注意：这些是「已经发生过的事」，不是当前待接的新消息，请勿当作本轮要回应的内容。

【线下场景总结 · 会话b2m6y9 · 第1–2条】
【绝密卷宗】我们约定过：小满最怕打雷，雷雨天要抱着她。
```

抬头只留一层，块头保住了，定位说明补齐了。

这个问题的**代码侧**修完了（溯源 + 定位说明）。
但那份「同源副本」本身要不要清，取决于你的意图：

- **如果你只是不想让线下思维链再读到它** —— 已经修好了，
  现在它至少会明确标着「线上记忆」来源，模型也不会再把它当待接内容。
- **如果你想彻底清掉** —— 去「记忆功能」或「记忆表格」里删掉对应总结。
  那份数据存在 `chatSettings.summaryList` / `megaSummaryList`，
  卷宗列表的删除按钮管不到它。
- **两者的区别**：删卷宗 = 删线下场次的正文与总结；
  删记忆总结 = 删线上那份沉淀。

## 四十一、教训

> **「删除」的语义边界，必须由设计者显式定义，不能留给用户猜。**

这次的问题表面看是「幽灵记忆」，本质是**同一份内容存了两处，
而删除只作用于其中一处**。用户的心智模型是「这段剧情我删掉了」，
系统的实现是「我删掉了 A 存储，B 存储原封不动」。

这类问题在代码审查里极难发现 —— 每一处的实现都是对的、
每一个测试都是绿的，错的是**它们之间的关系**没有被人审视过。

具体的改进：
1. 记忆块必须**自报来源**（本次加的 `【线上记忆-*】` 前缀），
   不能让两个来源的内容长得一模一样地躺在同一个块里；
2. 凡是「同一份内容写多处」的设计，删除入口要么做级联，
   要么在文档/UI 上明确告诉用户「这里删了那里还在」 ——
   最差的处理是沉默。

## 四十三、BUG-3 回滚的四个残余缺口（G1–G4）

第七批给 `applyBackupLocalStorage` 加了「快照 + 失败回填」，方向是对的，
但回填的**方向**和**覆盖面**都不够。

### G1 回填是单向的，写失败的 key 会永久消失

原实现：

```js
if (Object.prototype.hasOwnProperty.call(ls, k) && ls[k] != null) return;  // ← 直接跳过
```

只补「旧有、新包没带」的 key。而「新包要写、但**写失败**」的 key
被这句 `return` 跳过 —— 它在 `clear()` 之后**彻底消失**，
而导入前它可能好好的（备份包缺字段、或该版本还没这个 key）。

改成双向：新包要写、但确实没写进去的，也恢复旧值；
已经写成功的才跳过（别拿旧值盖掉新值）。

### G2 ZIP 导入路径根本没有失败提示

`importOneBackupZip` 拿到 `lsFailed` 后只塞进返回值，
调用方 `importBackupZipFiles` 不读它 —— 而 ZIP 恰恰是**主推**的导入方式
（JSON 路径 `restoreBackupPayload` 反而有 toast）。

### G3 快照失败 / clear 失败被静默吞掉

```js
} catch (eSnap) {}
try { localStorage.clear(); } catch (e0) {}
```

快照失败（隐私模式、配额已满）意味着**根本没有回滚能力**，
用户在完全无保护的情况下导入，却什么都不知道。
现在上报 `snapshotFailed` / `clearFailed`，调用方明确提示
「本次导入无回滚保护」。

### G4 快照漏掉溢写到 IDB 的 key

`miyaSafeLsSet` 在 localStorage 配额不足时会把值**溢出到 IDB**。
这些 key 已不在 localStorage 里，却是用户真实数据 ——
只遍历 `localStorage` 的快照会漏掉它们，回填时被当成「本来就没有」。
现在用 `miyaKeyNeedsAsyncHydrate` + `__miyaKvMem` 把它们纳入快照。

### 追加发现：回填用同一个函数救自己，会死锁

改完 G1 后写运行时验证（`audit_backup_rollback_runtime.py`），
强制让某个 key 写入失败，结果**回填也失败** —— 因为回填仍然走
`miyaSafeLsSet`：

```
导入前: {A: OLD-A, B: OLD-B, C: OLD-C}
写入:   B 强制失败
回填:   ✗ R2 新包写失败的 key（B）恢复旧值  —— B=None
```

> **用同一个函数去救它自己造成的现场，是一个死循环。**
> `miyaSafeLsSet` 失败的两个原因（配额满、隐私模式）恰恰也是回填失败的原因。

修复：回填**直写 `localStorage.setItem`**，绕过配额预检与溢出逻辑，
由浏览器自己裁决。旧数据一般比新数据小，直写成功率明显更高。
修好后 7/7：

```
导入后: {A: OLD-A, B: OLD-B, C: NEW-C, D: NEW-D}
  ✓ R1 本地独有旧 key（A）被回填
  ✓ R2 新包写失败的 key（B）恢复旧值
  ✓ R3 已写成功的新 key（C）保持新值
  ✓ R3 新包独有 key（D）写成功
```

## 四十四、BUG-2 遗留项：`collect(force)` 落地

原状：`collect: function (force) { return collectStorageContext(force); }`
但 `collectStorageContext()` **不接参数、也没有任何缓存**。
注释却写着「force=true 绕过缓存」—— 文档与实现不符比没有文档更糟：
调用方按注释以为拿到了新鲜数据。

修复：真加缓存 + force 语义落地。

```js
var STORAGE_CTX_TTL_MS = 4000;
collect()      → 4 秒内复用缓存（要遍历 localStorage + 多个 IDB 库，是重活）
collect(true)  → 强制重扫并写回缓存
invalidate()   → 真失效（原先因为引用了未声明变量，退化成空操作）
```

### 连带修掉：自己踩出来的「清完不刷新」

加了缓存之后立刻发现一个自伤：`clearStorageCategory` 里那长长一串
`invalidateCache` 调的是**别人**的缓存，唯独漏了自己 ——
清完分类紧接着刷面板会读到 4 秒内的旧数字，表现为「点了清理，用量没降」。
所有分类共用这一处出口，在函数末尾补 `invalidateStorageCache()`。
`compressAllChatImages` / `deleteAllChatImages` 同样处理。

## 四十五、DEF-4 的不对称是**正确的**

复核时发现一处看起来像疏漏的地方：

| 函数 | 剔除的清单 |
|------|-----------|
| `applyToChatSettings`（全局 → 会话） | 只剔 `SESSION_SCOPED_BM_KEYS` |
| `applyContactOverride`（表单 → perContact） | 剔 `CHAT_LEVEL_BM_KEYS` + `SESSION_SCOPED_BM_KEYS` |

查 `miya-chat-store.js:5050` 的 `getChatSettings()` 才明白为什么：

```js
// getChatSettings 的合并顺序是「全局 ⊕ 会话级名字段覆盖」
chatLevelBgKeys.forEach(k => { if (rawChatBg[k] != null) chatBgPatch[k] = rawChatBg[k]; });

```

- **全局 slice 里的 chatLevel 字段是无意义的** —— 它们永远被会话级盖掉，

**不对称是对的**，但原来的注释没把理由写清楚，容易被后来者当成疏漏
「顺手对齐」掉。已在 `applyContactOverride` 的注释里补齐这段推理。

## 四十八、教训

> **「修过了」和「修完了」是两件事。修复日志记的是意图，不是结果。**

这次复核最有价值的两条：

1. **回滚逻辑不能用「导致失败的同一手段」去执行。**
   `miyaSafeLsSet` 失败 → 用它回填 → 又失败 → 数据永久丢失。
   凡是「补救」路径，都要问一句：**它和被补救的失败共享哪些前提？**
   共享的前提越多，补救越可能一起失效。

2. **注释承诺的语义，要么实现它，要么删掉它。**
   `collect(force)` 的注释写着「force=true 绕过缓存」，
   而缓存压根不存在 —— 这种注释不是文档，是**误导**。
   它比没有注释更危险，因为读代码的人会信任它。

另外值得一提的是：这次 4 个缺口里有 2 个是**我在修 G1 的过程中自己踩出来的**
（回填死锁、清完不刷新）。这不是意外 —— 修 bug 的动作本身就会引入新状态，
所以每次修完都必须重新走一遍完整的运行时验证，而不是只跑改了的那条断言。

# 第十二批 · 删了卷宗，AI 为什么还记得（真修复）

## 四十九、先承认上一批的判断是错的

第十批结束时我说「代码侧修完了」，那句话**夸大了**。第十批实际做的是：

> 给线上来源的记忆块加上 `【线上记忆-xxx】` 前缀，让用户能分辨这块内容
> 来自「线下卷宗」还是「线上记忆功能」。

那解决的是**可辨认性**，不是**隔离**。我当时在注释里其实写下了实情 ——
「线上那份原封不动」—— 却没有把这个事实当成未完成的缺陷对待。

用户复查后回报：

> 是因为刚才那个记忆的同源副本没有清的原因吗，
> **ai 还是知道我发了和之前删的卷宗里发的同样的消息**

问题成立。本批做的是真正的隔离。

## 五十、回答用户的疑问：不是「同源副本」的问题

用户猜的方向是「线上那份同源总结没清」。这个猜测**部分成立但不是主因**，
因为还有一条更隐蔽、更严重的通路，它跟总结一点关系都没有。

先说一个反直觉的结论：

> **删除卷宗这个动作本身，会把过滤功能关掉。**

也就是说：**不删的时候反而更安全，删了才泄漏。** 下面拆开讲。

## 五十一、根因：镜像存续判断依附于「卷宗还活着」

线下剧情会以「镜像」形式写进线上聊天线程（带 `offlineMeet` 标记），
这是设计如此，目的是让线下发生过的事在线上也能接得上。

这些镜像**默认是进 API 上下文的**。`js1/miya-chat-store.js` 里
`getMessagesForApi` 的注释白纸黑字写着：

```js
/** API 上下文：含线下镜像消息（线上 UI 不展示）；排除朋友圈留痕占位 */
```

它**故意不排除** `offlineMeet`，把过滤工作交给下游
`MiyaAppointmentMemory.filterOfflineMirrorsForApiHistory`。

而下游的判定函数 `shouldKeepOfflineMirror` 的逻辑是
「**只滤掉已被线下总结区间覆盖的镜像**」：

```js
var ranges = filterCtx.sessionRanges[sid];
if (!ranges || !ranges.length) return true;   // ← 没有区间就放行
```

矛盾就出在这里。过滤上下文的来源是：

```
exportForMemory(chatId, contactId)
  → getSessionsByContact(contactId)
  → 只返回「还活着」的卷宗
```

**卷宗一旦被删除，它就不在这个列表里了**，于是：

1. `sessionRanges[sid]` 查不到 → 空
2. 第 255 行 `return true` → 放行
3. 镜像带着完整正文进入 API

删除动作亲手把过滤依据抽走了。这不是「同源副本没清」，
而是**过滤器依赖了一个删除后必然失效的信号**。

### 为什么第一眼看不出来

因为 `deleteSession` 里确实有清理镜像的代码
（`purgeSessionOnlineMirrors`），看着像是处理过了。
但它用的是**软删**：`updateMessage({ deleted: true, content: '' })`。

软删本身没问题（内容会被清空）。问题在于它有几条会打空：

| 打空场景 | 原因 |
|---|---|
| 宿主桶里找不到卷宗 | 原代码直接构造 `{messages: []}` 空壳，丢掉真实 `chatId` 与全部 `chatMirrorId`，第一路清理全部指错线程 |
| 卷宗已被迁移过 | `migrateSessionsToCanonicalChat` 把场次搬到 canonical chat，UI 还拿旧 `chatId` 调删除就落空 |
| 镜像的 `appointmentSessionId` 缺失 | 第二路全库扫描按这个字段认领，不等就扫不到 |
| 软删请求失败 | 进重试队列，但若一直失败则镜像永远保持 `deleted: false` |

任一条命中，镜像就以「活着且有内容」的状态留下来，
下次取 API 上下文时照常注入。

### 附带发现的第二条通路：卷宗复活

镜像存活还有个更糟的后果。`recoverSessionsFromChatMirrors`
会从**存活的镜像**反推重建卷宗 —— 这是给「存储丢了但聊天记录还在」
设计的恢复功能。它靠墓碑（`deletedSessionIds`）来跳过已删的卷宗。

于是形成一条完整回路：

```
软删打空 → 镜像存活（deleted:false）
        → 墓碑 30 天过期 / 被 500 条上限挤掉
        → recoverSessionsFromChatMirrors 把已删卷宗整卷重建
        → 用户看到「删过的卷宗自己回来了」
```

这也解释了用户可能遇到过的另一种怪现象。

## 五十二、修复：让删除留下一个过滤器能读到的信号

核心思路：**不能依赖「卷宗还在列表里」这个删除后必然消失的状态。**

墓碑（`deletedSessionIds`）是删除动作留下的**物理事实**，
与卷宗是否还在列表里无关，且已经持久化落盘。把它接出去即可。

### 改动 1 · 导出墓碑查询（`js1/miya-appointment-store.js`）

```js
isSessionTombstoned: function (sessionId) { ... },
getDeletedSessionIds: function () { ... },
```

### 改动 2 · 过滤上下文装载墓碑（`js1/miya-appointment-memory.js`）

`buildOfflineMirrorFilterContext` 新增两张字段：

```js
tombstoned: Object.create(null),   // 已删卷宗 id 集合
tombstoneKnown: false              // 墓碑表是否成功读到
```

装载放在函数**最前面**，即使后面因为拿不到 `contactId` 提前返回，
墓碑也已就位。

### 改动 3 · 判定函数改为分层（同文件）

```js
// ① 墓碑命中 → 丢弃（排在区间判断之前）
if (sid && filterCtx.tombstoned && filterCtx.tombstoned[sid]) return false;

// ② 不在活卷宗索引、也不在墓碑表 → 视为已删（不依赖 30 天 TTL）
if (sid && filterCtx.tombstoneKnown
    && !filterCtx.msgIndexById[sid] && !filterCtx.sessionRanges[sid]) {
    return false;
}

// ③ 孤儿镜像（无 appointmentSessionId）→ 丢弃
if (!sid) return false;
```

第 ② 条是专门对付墓碑过期的：墓碑有 30 天 TTL 与 500 条上限，
过期后第 ① 条就失效了。而「镜像自称属于某个 session，但该 session
既不在活卷宗索引里、也不在墓碑表里」——这已经是足够的删除证据。

第 ③ 条来自一个观察：正常写入（`mirrorMessageToChat`）**一定**会带
`appointmentSessionId`。缺失只可能来自旧数据或异常写入，
属于无法验证来源的孤儿，不该带着内容进上下文。

**关键安全阀**：第 ② 条只在 `tombstoneKnown` 为真时生效。

## 五十五、给用户的操作指引

1. **升级到本版本后**，以后再删卷宗，内容会真正不再进入对话上下文。
2. **对已经删除过的卷宗**：删除动作发生在旧版本，当时的镜像可能已经
   处于「存活且有内容」状态。需要用
   `diagnose-memory-leak.html` 查一下，若【5】节报出

## 五十六、教训

**教训一：我在第十批把「可辨认」当成了「已修复」。**

加溯源前缀确实有价值 —— 它让用户能定位来源。但用户报的是
「AI 还记得内容」，那要的是**内容不进上下文**。两件事被我混为一谈，
报告时也没有说清「这只解决了识别问题，隔离问题是独立的」。

正确的汇报方式应该是当时就写明：

> 本批只解决「分不清内容来源」，不解决「内容仍被读取」。
> 后者是独立缺陷，需要单独修。

**教训二：过滤器的依据不能是「删除后必然消失的状态」。**

`shouldKeepOfflineMirror` 依赖 `exportForMemory` 的返回，
而那个函数天然只返回活着的卷宗。这意味着过滤器在最需要它工作的时候
（内容已被删除）恰好失效。这类缺陷有个共同特征：

> **正常路径下功能是对的，异常路径下静默失效。**

而删除正是异常路径，所以测试时不容易撞到 —— 除非专门去构造。

**教训三：反直觉的因果要专门验证。**

「删除让内容更容易泄漏」这个结论第一眼很难相信。它成立的原因是
**删除同时移除了过滤依据**。遇到这种反直觉链条时，光靠读代码不够，
必须写一个能**先把 bug 复现出来**的测试（`删除前含密文 = True`），
否则你无法区分「本来就没问题」和「修好了」。

**教训四：给用户的自查工具，必须自己先验证它能报出已知数据。**

`diagnose-memory-leak.html` 前三次测试都报「0 个聊天线程」——
一个永远报「没问题」的诊断工具，比没有工具更危险。所以补了
`audit_diagnose_page.py`：先造一份已知的「已删卷宗 + 残留镜像」数据，
确认工具能报出来，再交给用户。

# 第十三批 · 「AI 说事件七，我哪里都找不到」

## 五十七、用户报告

> 我搞不明白 ai思维链说的记忆表 说事件七里已经发生过我刚才新建聊天重新发的一模一样
> 的内容了 但是我哪里找都找不到它说的事件七

这条报告和上一批（第十二批）不同：上一批是**线下卷宗**的内容泄漏，
这一批是**记忆表格**，两者是**完全独立的两套存储**，泄漏原理也不一样。

## 五十八、先定位「事件七」是什么

全仓库搜「事件七」没有任何结果 —— 它不是代码里的固定字样，是**数据**。
继续查 `js2/miya-memory-table-store.js`，找到了：

```js
{
  id: 't_event',
  name: '重要事件',                        // ← 就是它
  note: '只记录对后续剧情有影响的事件。',
  columns: ['相关角色', '事件简述', '时间', '地点', '情绪'],
  rows: []
}
```

记忆表格内置五张表，「重要事件」是第四张。注入给模型时，`tableToCsvBlock`
把它序列化成带 `rowIndex` 的 CSV：

```
* 3:重要事件
【表格内容】
rowIndex,0:相关角色,1:事件简述,2:时间,3:地点,4:情绪
0,小满,……,……,……,……
…
6,小满,【绝密】去年海边约定,去年夏,海边,温柔
```

所以 **AI 说的「事件七」= 这张表的第 7 行（rowIndex 6）**。
它确实存在，只是不在用户找的地方。

## 五十九、为什么「哪里都找不到」

三层原因，一层比一层隐蔽。

### 原因一：记忆表格和聊天记录是两套独立存储

| 数据 | 存储键 |
|---|---|
| 聊天消息 | `miya-chat-meta` |
| 记忆索引（分镜/大总结/角色记忆） | 聊天设置里 |
| **记忆表格** | **`miya-memory-tables-v1`** |

用户在聊天记录里翻，而「事件七」在记忆表格里 —— 不同 App、不同入口、
不同存储。而且记忆表格界面**只在聊天工具栏深处**才能打开。

### 原因二：`clearChatMessages` 清了记忆索引，唯独没清记忆表格

这是真正的缺陷。看「清空聊天记录」这个动作的清理范围：

```js
clearChatMessages: function (chatId) {
    metaCache.messagesByChat[cid] = [];        // ✅ 消息
    ...
    return store.saveChatSettings(cid, {
        summaryList: [],                        // ✅ 分镜
        megaSummaryList: [],                    // ✅ 大总结
        charMemoryList: []                      // ✅ 角色记忆
    });
    // ❌ 记忆表格 miya-memory-tables-v1 —— 完全没提
}
```

用户的实际经历很可能是：

1. 和小满聊过一段，AI 往「重要事件」表里写了 7 行
2. 用户**清空了聊天记录**（以为一切都清了）
3. 重新发一模一样的一句话
4. AI 从记忆表格里读到「事件七」，回他「这在事件七里已经发生过」
5. 用户去聊天记录里翻 —— 当然找不到，它在另一个存储里

**`clearChatMessages` 清了消息也清了记忆索引，说明作者的意图就是「这个角色的记忆清空」。
但记忆表格是按 chatId 分桶的另一个键，收口时被漏在外面。**
同一个意图，清理范围不一致。

### 原因三：界面标题根本对不上是谁

```js
title.textContent = '记忆表格 · ' + (state.chatId || '').slice(-6);
```

只显示 **chatId 后 6 位**，类似 `记忆表格 · foxkak`。
用户看到这个，既不知道这是哪个角色，也不确定是不是自己要找的那个。
即使他摸到了记忆表格界面，也对不上号。

## 六十、还有一个更根本的行为需要说明

`createChat` 对**同一个联系人是幂等的**：

```js
var existing = store.findChatByContact(o.contactId);
if (existing) return existing;      // ← 直接返回已有聊天，不新建
```

所以用户说的「新建聊天」，如果是对**同一个角色**操作，它并不会产生新会话 ——
拿回来的是同一条 chat，记忆表格也是同一个桶。这解释了另一半困惑：
**为什么"新建"之后 AI 还记得。**

这是设计如此（一个联系人一条私聊线程，避免多面具/历史重复导致上下文错乱），
但它和用户对「新建」的直觉不一致。本批不改这个行为（改了会引发更严重的
重复线程问题），而是通过界面提示把事实讲清楚。

## 六十一、修复

### 改动 1 · `clearChatMessages` 一并清空记忆表格（`js1/miya-chat-store.js`）

```js
return chain.then(function () {
    try {
        var mtStore = global.MiyaMemoryTableStore;
        if (mtStore && typeof mtStore.resetChat === 'function') {
            return mtStore.resetChat(cid).then(function () { return saveMeta(); });
        }
    } catch (eMt) {}
    return saveMeta();
});
```

用 `resetChat` 而非 `dropChat`：保留桶与表结构，用户下次进来仍是熟悉的五张空表，
只是行清空了。这样「清空聊天记录」终于覆盖了它声称覆盖的全部范围。

### 改动 2 · 新增 `dropChat` / `listChatIds`（`js2/miya-memory-table-store.js`）

```js
function dropChat(chatId) { /* 整桶移除，不留空壳 */ }
function listChatIds() { return Object.keys(loadAll().chats || {}); }
```

`dropChat` 与 `resetChat` 的区别是刻意保留的：前者连桶一起删（用于删除场景），

### 改动 4 · `removeContact` 清理该角色名下所有桶（同文件）

记忆表格是**唯一一个按 chatId 而非 contactId 分桶**的派生记忆，
所以在 `purgeContactScopedData` 里它需要特殊处理：先按 contactId 反查 chatId，
再逐个 drop。群聊里该角色是成员的那些桶也一并清。

**这里踩了一个真实的坑**（第一版实现失败）：

```
V3 删除联系人前的桶数   1
V3 删除联系人后的桶数   1     ← 没清掉
```

原因是 `removeContact` 的执行顺序：

```js
var chatIds = metaCache.chats.filter(...).map(...);   // ① 先算出 chatIds
metaCache.chats = metaCache.chats.filter(...);        // ② 立刻把它过滤掉
...
var purgeDone = purgeContactScopedData(key);          // ③ 这里已查不到 chatId
```

第 ② 步之后就再也拿不到这个角色的 chatId 了。修法是把 ① 算好的列表
显式传进 `purgeContactScopedData(key, knownChatIds)`。

> **教训**：清理函数依赖「调用时会话列表还没被改」是个隐性契约。
> 一旦调用顺序变化就静默失效 —— 而且失效方向是「该删的没删」，
> 不会有任何报错。

### 改动 5 · 界面可辨识性（`js2/miya-memory-table-app.js`）

标题从 `记忆表格 · foxkak` 改为 `记忆表格 · 小满（foxkak）`：

```js
function describeChat(chatId) {
    // 私聊取联系人名，群聊取群名，拿不到退回「未命名」
    // 附带 id 尾号，便于对照聊天记录排查
    return out + '（' + cid.slice(-6) + '）';
}
```

并在标题下新增一行**作用域说明**：

> 本表只属于「小满（foxkak）」——记忆表按聊天分开存，别的聊天看不到这里的行，反之亦然。
> 其他聊天的记忆表：[小满（…）（事件 7 条）] [阿澈（…）（事件 0 条）]

「其他聊天」是可点的按钮，直接切过去。这样用户既知道自己看的是谁，
也知道还有别处 —— 不需要靠猜。

## 六十四、给用户的操作指引（针对已存在的「事件七」）

本批修的是**以后不再发生**。你记忆表里已经有的那几行还在，需要手动清：

1. 打开 `diagnose-memory-leak.html` 点「开始诊断」，
   看【6】章节确认「事件七」在哪个聊天的「重要事件」表里。
2. 到那个角色的聊天里打开**记忆表格**界面，切到「重要事件」页，
   找到那一行点「删」。
3. 更省事的做法：在那个角色的聊天设置里点一次**「清空消息」** ——
   升级后会连带把记忆表一起清空。
4. 如果你根本不想要记忆表格这个功能，在记忆表格界面把顶部的
   **「AI 读取」**关掉，它就不会再注入上下文（数据留着但不生效）。

另外说明一下「新建聊天」：对**同一个角色**新建，不会产生第二条会话
（设计如此，避免重复线程），所以记忆是延续的。想要全新开始，
用「清空消息」或「删除联系人」。

## 六十五、教训

**教训一：同一个用户意图，清理范围必须一致。**

`clearChatMessages` 清了消息、清了分镜、清了大总结、清了角色记忆，
唯独漏了记忆表格。这说明作者**想到了**「要清派生记忆」这件事，
只是因为记忆表格按 chatId 分桶（和其他按 contactId 分桶的不一样），
在手工枚举时被漏掉。

> 凡是「手工列清单」的清理逻辑，早晚会漏。
> 要么维护一张集中的「派生数据注册表」，要么每次新增存储时强制回填清理点。

**教训二：隐性契约导致的静默失效最危险。**

`purgeContactScopedData` 依赖「调用时 `metaCache.chats` 里还有这个角色」，
而 `removeContact` 在调用它之前就把 chats 过滤掉了。
这种 bug 不报错、不警告，只是**该删的没删**。
我的第一版修复正是踩在这上面（V3 测试 1 → 1）。

**教训三：探索性测试的断言要区分「期望」和「实测」。**

我最初写 `audit_memory_table_chat_bucket` 时假设「两次 createChat 会得到不同
chatId」，结果 2/5 失败。但失败的是**我的假设**，不是代码。
把它改成记录实测行为（幂等复用），它就从一个假失败变成了有价值的文档 ——
它现在明确写下了「为什么新建聊天后 AI 还记得」。

**教训四：给用户报错误编号时，要说清是 0-based 还是 1-based。**

AI 看到的 `rowIndex` 从 0 开始，用户说的「第七件」从 1 开始。
差了 1 就足以让人找不到东西。诊断页现在两种都标。
