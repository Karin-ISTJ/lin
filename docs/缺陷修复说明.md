## 二、缺陷 1 —— 整桶注入文本丢失（核心）

### 现象

同一深度桶（前/中/后）里，只要存在一条 `globalReach='all'` 且 `key=['']` 的词条，
**该桶的注入文本会整段消失**，而同批词条仍出现在 `matched` 数组里 —— 面板显示「已命中」，
实际 prompt 里什么都没有。完全静默，无报错。

### 复现（真实浏览器 A/B 对照）

世界书放三条，`back` 桶：`e3`（全软件，`key=['']`）+ `e4`（普通词条，`key=['苹果']`，本轮命中）。

**修复前** —— `matched` 说命中了 `e4`，但 `text` 里没有它：

```
matched: ['e1', 'e2', 'e3', 'e4']
text: 【世界书·前·全局设定】
- 同桶陪衬: 这是陪衬内容          ← back 桶整段消失
```

**修复后**：

```
matched: ['e1', 'e2', 'e3', 'e4']
text: 【世界书·前·全局设定】
- 空关键词设定: 这是空关键词内容   ← back 桶回来了
- 同桶陪衬: 这是陪衬内容
```

### 根因

`js2/miya-worldbook-prompt.js` 中 `entryHasKeys()` 手写了一份判据，与 `matcher.entryKeywords()` **不等价**：

```js
// prompt.js（错误）
var k = Array.isArray(entry.key) && entry.key.length ? entry.key : (entry.keywords || []);
return Array.isArray(k) && k.length > 0;        // 只看数组长度，不剔空串

// matcher.js（权威）
if (Array.isArray(entry.key) && entry.key.length) return entry.key.filter(Boolean);  // 剔除空串
```

于是 `key=['']` 时两边结论相反：

- `prompt.js` 认为「**有关键词**」→ 丢进 `keywordPool` 参与关键词匹配 → 永远匹配不上 → 本轮被判不注入
- `matcher.js` 认为「**无关键词**」→ 走 `reach==='all'` 常驻分支直接放行

两条路都拿不到它，而 `buildWorldbookPrompt` 末尾又用 `merged` 去分桶，
于是 `buckets[该深度]` 为空，**同桶其它词条被一起吞掉**。

### 修复

统一到唯一判据，禁止各写一份：

```js
// matcher.js 新增，作为全链路唯一权威判据
function hasAnyKeywords(entry) {
  return entryKeywords(entry).length > 0;   // entryKeywords 已 filter(Boolean)
}

// prompt.js 改为委托，不再自己算
function entryHasKeys(entry) {
  if (matcher && typeof matcher.hasAnyKeywords === 'function') {
    return matcher.hasAnyKeywords(entry);
  }
  return false;
}
```

## 三、缺陷 2 —— 运算符优先级写错

`js2/miya-worldbook-matcher.js` 第 180 行附近：

```js
// 错误写法：|| 优先级低于 &&，实际等价于 (constant || 无关键词) ? true : stKeywordMatch()
return entry.constant || !(entry.key && entry.key.length) && !(entry.keywords && entry.keywords.length)
  ? true
  : stKeywordMatch();
```

`stKeywordMatch()` 内部走 `st.activateEntries`，对无关键词词条返回空数组 → `false`。
叠加旧判据后，`key=['']` 的全软件词条掉进这里被判负。

修复：补括号，并改用统一判据。

```js
return entry.constant || !hasAnyKeywords(entry)
  ? true
  : stKeywordMatch();
```

同时修掉同一函数局部分支里第三份不等价写法（`entry.key.length` 未剔空串）：

```js
// 局部词条：绑定角色后若「真的没有关键词」应常驻
if (bound.length && !entryKeywords(entry).length) return true;
```

## 四、缺陷 3 —— 新建片段默认状态导致永久不注入

### 现象

用户点「新建片段」→ 填名字和正文 → 保存。词条**永远不会出现在任何 prompt 里**，且 UI 不给任何提示。

### 根因

`js2/miya-worldbook-app.js` 新建片段时 `data` 对象**没有 `constant` 字段**：

```js
var data = entry || {
  scope: ..., globalReach: 'online_offline', depth: 'middle',
  keywords: [], boundRoleIds: [], enabled: true,
  // ← 无 constant
};
...
if (data.enabled === false) statusEl.value = 'disabled';
else if (data.constant) statusEl.value = 'constant';
else statusEl.value = 'normal';          // ← undefined 落在这里 → 下拉显示「关键词触发」
```

保存时：

```js
constant: status === 'constant',   // false
keywords: [],                       // 用户没填（UI 也没说必须填）
```

→ `matchEntry` 走 `reach='online_offline'` 分支 → `stKeywordMatch()` → **`no_keywords` 拒绝**。

`explainEntry` 的诊断原文：

```
reason: no_keywords
detail: 该词条非常驻，但没有配置任何关键词，永远不会被触发
```

更微妙的是 `index.html` 里状态下拉的**第一项是「常驻」**，视觉上看起来默认就是常驻，
但代码的 `else` 分支把它覆盖成了「关键词触发」—— **UI 与代码默认值不一致**。

### 修复

在新建片段的对象里显式声明默认值，与下拉第一项对齐：

```js
enabled: true,
/* ⚠️ 新建片段默认「常驻」。缺省会让 statusEl 落进 else 分支显示「关键词触发」，
   而用户新建时通常不会填关键词，于是被 no_keywords 拒绝，词条永远不注入且毫无提示。 */
constant: true,
```

> **行为变更提示**：修复后「新建片段」默认状态为**常驻**，创建即生效。
> 若此前有依赖旧默认值的既有数据 —— 不受影响，旧数据 `constant` 字段已被 store 归一化为 `false`，
> 只是这些词条本来就一直不生效。需要它们生效的话，手动把状态改成「常驻」或补上关键词。

## 五、未改动 / 澄清项

调查中确认以下行为**是设计意图，不是缺陷**，未做改动：

- **无关键词 + 非常驻的普通全局词条不注入**：`no_keywords` 拒绝是有意设计，
  避免「没配触发条件的词条无条件污染所有 prompt」。
- **`scope='local'` 且未绑定角色时不注入**：`roleMatches` 在 `bound` 为空时返回 `true`（不限角色），
  但 `listSortableWorldbookEntriesForContact` 会用 `if (!roleIds.length) return;` 提前过滤。
  两者对「局部词条未绑定角色」的处理不一致，但当前无 UI 路径能产生这种数据，属潜在隐患，
  本次未改，留作后续。
- **`key=[' ']`（纯空白）**：`entryKeywords` 只做 `filter(Boolean)`，不过滤纯空白串。
  已统一到该函数，行为一致；是否需要更激进的 trim 过滤属产品决策。

# 第二批：对话 API 预设保存

## 八、缺陷：保存预设后，返回再进来就没了

### 现象

用户在「对话 API → 接口预设」里点 ✓ 保存：

1. toast 提示「预设已保存」✓
2. 当前面板的下拉里确实出现了新预设 ✓
3. **返回上一级、或切走再回来 → 下拉变空了** ✗
4. 整页刷新后同样是空的 ✗

用户感知就是「保存预设后发现没保存到」。**数据其实一直好好躺在 IndexedDB / localStorage 里** ——
丢的是渲染用的那份列表。

### 复现（真实浏览器，走完整 UI 流程）

```
先进面板（此时预设为空）  → 下拉 ['']                              
点 ✓ 保存「竞态预设」      → 下拉 ['', '竞态预设']   看起来成功了
查盘                      → ['竞态预设']            数据确实在
返回 → 重进面板            → 下拉 ['']               ✗ 预设不见了
```

### 根因：`ensureReady()` 返回的是「首轮快照」，被拿去重绘

`js2/miya-api-config.js` 的 `ensureApiPresetsReady()` 返回一个**只 resolve 一次**的 promise，
闭包里捕获的是**首次加载时的那个数组对象**：

```js
apiPresetsReady = loadApiPresetsArr().then(function (list) {
  if (!Array.isArray(apiPresetsCache)) apiPresetsCache = list.slice();
  return apiPresetsCache;      // ← 首次加载的对象，之后永远不再变
});
```

而 `upsert()` 每次都是 `apiPresetsCache = list.slice()` —— **换了新对象**，老 promise 仍指向旧的
（首次进入时为空的那个）数组。于是必经路径必然踩坑：

```
先进面板（预设为空，promise 固化为 []）
  → 保存一条（apiPresetsCache 换成新的非空数组，promise 不变）
  → 返回再进 → hydrateApiPresets 拿 ensureReady() 的返回值重绘
  → 拿到首轮的 []，把正确的下拉覆盖成空
```

实测打桩输出，一眼可见两处数据不一致：

```
getCached()   → ['追踪预设']    ← 内存缓存是对的
ensureReady() → []              ← 仍是首轮快照
```

**同一个 bug 在这个模块里已经复发过三次**，每次都是「拿 `ensureReady()` 的返回值当数据用」：

| 次序 | 位置 | 状态 |
|------|------|------|
| 1 | `upsert` / `remove` | 已修（改走 `enqueueApiPresets` 串行队列） |
| 2 | `find` | 已修（`ensureReady().then` 里重新读 `apiPresetsCache`，注释写明了原因） |
| 3 | **`hydrateApiPresets`** | **本次修复** |

### 修复

**数据层** —— `ensureReady()` 已就绪时 resolve **当前**缓存，不再吐旧快照：

```js
function ensureApiPresetsReady() {
  if (apiPresetsReady) {
    /* 已就绪：直接返回「此刻」的缓存，而不是当初那个快照 */
    return Promise.resolve(apiPresetsCache || []);
  }
  ...
}
```

**UI 层** —— `hydrateApiPresets` 显式再读一次 `getCached()`，双保险，也让意图清楚：

```js
Promise.resolve(ready).then(function () {
  if (!presetPickEl()) return;
  /* ★ 必须重新读 getCached()，不能用 ensureReady() 的返回值 */
  var list = mod.getCached ? mod.getCached() : null;
  refreshApiPresetOptions(list || []);
}).catch(function () {});
```

### A/B 对照

回滚这两处修复后跑新增回归测试：**4 项失败**，且失败项正是核心场景：

```
· 返回后重进，预设仍在（曾经的失败点）   ✗
· 四条预设全部保留                       ✗
· 已删除的不再出现                       ✗
· 落盘列表与下拉一致                     ✗
```

修复后 14/14 全通过。

# 第三批：切换预设后点保存，却又变回切换之前

## 十、缺陷：切换预设后点保存，配置被回退

### 现象（用户原话）

> 「我切换了对话 api 的预设，结果一点保存，却没切换成功，
>   变回来切换之前的 URL 和 key。」

注意现象里的关键词：**「变回来切换之前的」**。这不是"没保存"，而是**保存把旧值又写了一遍**。

### 复现

用界面真实操作，正式配置为「线路A」，再存一条「线路B」：

| 步骤 | 正式配置 | 表单显示 |
|---|---|---|
| 1. 下拉切到线路B | A | **B** ← 只活在 DOM 里 |
| 2. 点返回（或切别的子视图） | A | 节点被销毁，**B 丢失** |
| 3. 再进来 | A | **A** ← 从正式配置重绘 |
| 4. 点保存 | **A** | 保存的是 A |

### 根因

三个环节缺一不可，所以这个 bug 很绕、也很容易只修一半：

**① 「载入预设」按设计只改 DOM，不动正式配置**

`applyApiPresetToForm()` 的注释写得很清楚：载入是一次**可反悔的预览**，用户随后点「保存」才生效。
所以切换后的线路**只活在 DOM 里**。

**② 多处路径会整块重绘，把 DOM 里的值销毁**

`render()` 对子视图是 `body.innerHTML = renderSubView(...)` —— **整块换掉**。而这些路径都会触发它：

- `closeSubView()` —— 点返回
- `openSubView()` —— 切到别的子视图 / 再进来
- `open()` 链里的异步 `scheduleRender()` —— **用户不动界面也会触发**

**③ 重绘时的初值取自「正式配置」**

```js
function renderApiChatSub() {
  var cfg = (global.miyaGetApiConfigCached && global.miyaGetApiConfigCached()) || {};
  // ...
  '<input ... id="mq-api-base" value="' + esc(cfg.baseUrl || '') + '">'
```

正式配置在点保存前不会变，所以重绘出来的一律是**切换前的旧线路**。

三者叠加：切换 → 重绘丢值 → 从旧值重绘 → 保存写回旧值。**全程零提示，因为每一步都"成功"了。**

---

### 修复过程：我第一版修错了方向

这一节如实记录一次**返工**，因为结论对后续维护很重要。

#### 第一版（错误）：给中间态打补丁

我按「返回 = 未保存编辑应当存活」的直觉，引入**子视图表单草稿** `state.subViewDraft`，
配套 `SUB_VIEW_DRAFT_FIELDS` 字段表与 `captureSubViewDraft` / `applySubViewDraft` /
`setSubViewDraftField` / `clearSubViewDraft` 四个函数，在 `render()` 换 innerHTML 前后抓取、回填。

测试 16/16 通过。**但这是给一个多余的设计打补丁。**

#### 用户第二轮反馈：出现了新症状

> 「还是不行啊 而且一点保存 保存的预设都没了 但是重进又会显示出来」

这是我改动**引入的副作用**：`applySubViewDraft` 拿草稿里的 `__presetName` / `__presetPick`
回填下拉框，与重绘后重建 `<option>` 的时序错位，把列表刷成空。
**数据在磁盘里没丢**（所以"重进又会显示出来"），只是 DOM 被刷没了。

#### 真正的根因：迁移时凭空造出了一个中间态

用户随后提供了旧包 `karinn-imagegen-v5-细线图标版`，并说明：

> 「以前对话 api 设置是好的，但是后来把这个功能移过来的时候漏了预设功能，又重新补了。」

拿旧包做基线 diff，关键差异一目了然 —— **旧包的预设选中就直接写正式配置，压根没有中间态**：

```js
// 旧包 js2/miya-settings-app.js
presetPick.addEventListener('change', function () {
  var name = presetPick.value;
  if (!name) return;
  ensureApiPresetsReady().then(function (list) {
    var pr = (list || []).filter(function (x) { return x && x.name === name; })[0];
    if (!pr || !pr.config) { toast('未找到该预设'); return; }
    setApiConfig(pr.config);          // ← 选中即刻写正式配置，一步到位
    syncFormsFromConfig();
    persistSystemPrefs();
    toast('已载入「' + name + '」');
  });
});
```

另外旧包还做过两件被漏掉的事：预设里存的是**整份 config**（`{ name, config, savedAt }`），
以及温度滑块的数值标签联动（`syncTempLabel`）—— 拖滑块只有条动、数字不动。

所以：**「载入 = 预览、点保存才生效」这个中间态是迁移时新造的，不是原有设计。**
它凭空制造了「只活在 DOM 里的值」，再叠加 `render()` 的整块重绘，才长出这一串 bug。
第一版的草稿补丁正是在为这个多余设计兜底 —— 属于治标，且自身引入了新缺陷。

### 最终修复：对齐旧包，选中即生效

撤销全部草稿机制，把 `loadApiPresetFromPick()` 改成一步到位：

```js
function loadApiPresetFromPick() {
  var mod = global.miyaApiPresets;
  var pick = presetPickEl();
  var name = pick ? String(pick.value || '').trim() : '';
  if (!mod || !name) return;
  mod.find(name).then(function (p) {
    if (!p) { toast('预设不存在'); return; }
    /* 写进正式配置并落盘 —— 这一步是「立即生效」的全部含义 */
    if (typeof global.miyaSetApiConfig === 'function') {
      global.miyaSetApiConfig(presetToConfigPatch(p));
    }
    applyApiPresetToForm(p);
    syncTempLabel('#mq-api-temp', '#mq-api-temp-lbl');
    syncTempLabel('#mq-api2-temp', '#mq-api2-temp-lbl');
    var nameEl = pageEl && pageEl.querySelector('#mq-api-preset-name');
    if (nameEl) nameEl.value = name;
```

配合一个字段映射函数，保证「保存预设」写进去的形状与「载入预设」读出来的形状永远对称：

```js
function presetToConfigPatch(p) {
  if (!p) return {};
  var out = {};
  if (p.baseUrl != null) out.baseUrl = String(p.baseUrl);
  if (p.apiKey != null) out.apiKey = String(p.apiKey);
  if (p.model != null) out.model = String(p.model);
  if (p.temperature != null) out.temperature = p.temperature;
  if (p.fallbackBaseUrl != null) out.fallbackBaseUrl = String(p.fallbackBaseUrl);
  if (p.fallbackApiKey != null) out.fallbackApiKey = String(p.fallbackApiKey);
  if (p.fallbackModel != null) out.fallbackModel = String(p.fallbackModel);
  if (p.fallbackTemperature != null) out.fallbackTemperature = p.fallbackTemperature;
  out.fallbackEnabled = !!p.fallbackEnabled;
  return out;
}
```

同时把旧包有、迁移时丢掉的**温度标签联动**补回来（载入预设是直接写 `input.value`，
不触发 `input` 事件，标签不会自己更新）：

```js
function syncTempLabel(rangeSel, labelSel) {
  if (!pageEl) return;
  var r = pageEl.querySelector(rangeSel);
  var l = pageEl.querySelector(labelSel);
  if (r && l) l.textContent = String(r.value);
}
```

**核心思路**：不要跟 `render()` 的整块重绘对抗 —— 只要「载入」这一步就把值写进**唯一的真源**
（正式配置 + 落盘 + 缓存），此后无论重绘多少次、从哪条路径重绘，读到的都是同一份正确数据。
没有中间态，就没有"中间态丢失"这一类 bug。

## 十三、关于「回归」判断的说明

你给的 zip 是云端签名链接，沙箱内拿不到原始基线，因此**无法做基线 diff**。
三批缺陷的判断依据都是**代码内部一致性**：

- 世界书：同一判据在三处各写一份、结论互不相同；UI 默认值与代码分支自相矛盾
- 预设保存：`ensureApiPresetsReady()` 的返回值语义与所有调用方的预期不符
- 本次：`render()` 的「整块换 innerHTML」与「载入预设只改 DOM」两个设计相互冲突

这类内部矛盾本身就是缺陷证据，可直接定位与修复。但**「是哪个版本引入的」无法确证** ——
这一点如实标注，不臆测。
